Install Pigsty on one Linux node. Read the setup guide in an ASD-STE100-inspired style.

Use this guide to install Pigsty on one Linux node. Start with Quick Start. A node with 1 CPU core and 2 GB of memory is sufficient.

You can use a Linux MiniPC, a cloud server, Windows WSL, or a virtual machine on your laptop. Pigsty supplies Vagrant templates for local virtual machines. It also supplies OpenTofu templates for cloud servers.

The single-node installation includes these features:

  • 600 PostgreSQL extensions.
  • Grafana and Victoria monitoring services.
  • Infrastructure as code for deployment.
  • Local point-in-time recovery (PITR).

External object storage can keep PostgreSQL backups outside the node. These backups improve data durability for demonstrations, personal websites, and small services. A single node cannot provide high availability. Automatic failover requires at least three nodes.

Quick Start

  1. Prepare a node with a supported Linux operating system.
  2. Use an administration account with passwordless SSH and sudo access.
  3. Run the commands below.
curl -fsSL https://repo.pigsty.io/get | bash  # Install Pigsty and dependencies
cd ~/pigsty; ./configure -g                   # Generate config (with 1-node template, -g generates random passwords)
./deploy.yml                                  # Execute deployment playbook

The installation script downloads Pigsty and installs its dependencies. The configuration script creates pigsty.yml and generates random passwords. The deployment playbook installs the modules in the configuration file.

You can also select a configuration template. The template supplies the initial configuration.

After deployment, do these tasks:

  • Open the Web UI.
  • Connect to PostgreSQL.
  • Apply the security recommendations.
  • Change the configuration to add more clusters.
  • Run playbooks to apply the configuration.

1 - Single-Node Installation

Install, configure, and deploy Pigsty on one Linux node.

This guide installs Pigsty on one Linux node. Single Node For production deployments with multiple nodes, use the Deployment Guide.

The procedure has three stages: Install, Configure, and Deploy.

Summary

Prepare a node with a supported operating system. Use an administration account with passwordless SSH and sudo access.

Select a download source and run its command:

pigsty.io (Global)
curl -fsSL https://repo.pigsty.io/get | bash
pigsty.cc (China)
curl -fsSL https://repo.pigsty.cc/get | bash

The installation script downloads and extracts Pigsty into your home directory. It also installs the deployment dependencies.

Then do these steps:

Enter the Source Directory

Run this command:

Terminal
cd ~/pigsty

Generate the Inventory

Run this command to generate the configuration file and random passwords:

Terminal
./configure -g

If you already have a prepared pigsty.yml, skip this step.

Run the Deployment Playbook

Run this command:

Terminal
./deploy.yml

After deployment, open the Web UI through Nginx on port 80 or 443. Use the node IP address or domain name. Connect to the default PostgreSQL service on port 5432.

The procedure usually takes 3–10 minutes. The duration depends on the server resources and network speed. Offline installation can reduce the duration. If you do not need monitoring, use Slim Installation to install fewer components.

Install

Use one of these commands to install Pigsty into ~/pigsty. The script also installs Ansible and other deployment dependencies.

pigsty.io (Global)

You can also download a release or clone the source repository. If you use Git, select a released version before deployment:

Terminal
git clone https://github.com/pgsty/pigsty; cd pigsty;
git checkout v4.5.0;  # Always checkout a released tag when using git

If you download or clone the source manually, run bootstrap to install the dependencies:

Terminal
./bootstrap           # Install ansible for subsequent deployment

You can also install Ansible manually.

Configure

The inventory defines the deployment. Pigsty uses pigsty.yml as the default inventory file. Edit this file to change the deployment configuration.

The configure script is an optional configuration wizard. It generates an inventory from your environment and input. Run it with -g to generate random passwords:

Terminal
./configure -g                # Use config wizard to generate config with random passwords

The default output file is ~/pigsty/pigsty.yml. Examine this file and make the necessary changes before deployment.

Use the configuration templates as examples. You can also edit pigsty.yml directly without the wizard.

Terminal
./configure                  # Default template, install PG 18 with essential extensions
./configure -v 16            # Use PG 16 instead of default PG 18
./configure -c rich          # Create local repo, download all extensions, install major ones
./configure -c slim          # Minimal install template, use with ./slim.yml playbook
./configure -c app/supa      # Use app/supa self-hosted Supabase template
./configure -c ivory         # Use IvorySQL kernel instead of native PG
./configure -i 10.11.12.13   # Explicitly specify primary IP address
./configure -r china         # Use China mirrors instead of default repos
./configure -c ha/full -s    # Use 4-node sandbox template, skip IP replacement/detection

The output below is from v4.5.0. If you install a different version, the first line shows that version.

Common configure Arguments

-i | --ip , IPv4

Set the primary private IPv4 address of the current node. The script replaces 10.10.10.10 in the inventory with this address.

-c | --conf , string

Select a configuration template relative to conf/. Omit the .yml suffix.

-v | --version , integer

Select a PostgreSQL major version from 14 through 19. PostgreSQL 19 is Beta. Use the dedicated pg19 template for that version.

-r | --region , enum , defaultdefault

Select the upstream repository region: default, china, or europe. Use the region that gives faster downloads.

-n | --non-interactive , boolean , defaultfalse

Supply the primary IP address through command-line arguments. Skip the interactive wizard.

-x | --proxy , boolean , defaultfalse

Use the current environment variables to configure proxy_env.

If the node has multiple IP addresses, specify the primary address with -i|--ip <ipaddr>. You can also enter the address at the interactive prompt. Use a static private IPv4 address. Do not use a public IP address.

Replace default credentials before deployment

Default credentials are public. Replace them in pigsty.yml before deployment. See Security Recommendations for the credentials that configure -g does not replace.

Upstream repository changes can stop installation

Changes to Linux or PGDG repositories can break package dependencies. If installation fails for this reason, wait for the upstream correction. You can also use offline packages.

Repeated deployment can change running services

If Pigsty is already deployed, another run of deploy.yml can restart services. It can also overwrite configuration files. Examine the required changes before you run the playbook again.

2 - Docker Deployment

Run Pigsty in a Docker container for local development and testing.

Pigsty runs on native Linux. It can also run in Linux containers with systemd. If you use macOS or Windows, use Docker to try a local single-node installation.

cd ~/pigsty/docker
make launch          # Start container + generate config + deploy

After deployment, use these addresses and commands to connect:

Suitable uses
  • Try Pigsty on macOS or Windows.
  • Learn, test, develop, or debug Pigsty features.
  • Run a local PostgreSQL development environment.
Deployment limits

This single-node container does not provide high availability across multiple nodes. For production or large deployments, use native Linux virtual machines or physical servers. Native Linux avoids the container and virtualization overhead of this testing environment.

Image

Pigsty supplies the pgsty/pigsty image on Docker Hub.

The image supports amd64 (x86_64) and arm64. The ARM architecture includes Apple Silicon and AWS Graviton. Image tags follow Pigsty versions. The latest and v4.5.0 tags point to the current release. Select a version tag for repeatable deployment.

The image uses Debian 13 (Trixie). It includes systemd, SSH, the pig command-line tool, Ansible, and initialized Pigsty source. The Docker configuration template prepares it for ./deploy.yml.

Use the commands in the docker/ directory. The make launch command starts the container, generates its configuration, and runs deployment:

cd ~/pigsty/docker

./deploy.yml         # Execute deployment

To build the image locally, use these commands:

cd ~/pigsty/docker
make build           # Build image locally
make launch          # Start container + generate config + deploy

To start the container with docker run, use this command:

You can also use the Makefile command:

make run          # Start with docker run
make exec         # Enter container
make clean        # Stop and remove container
make purge        # Remove container and directly delete ./data in the current directory

How It Works

The image uses Debian 13 (Trixie) with systemd as the initialization system. Manage services inside the container with systemctl, as on native Linux.

The container has these properties:

  • Systemd manages the services.
  • SSH permits root access with the password pigsty.
  • The --privileged option supplies the access required by systemd.
  • The /data volume keeps data outside the container.
  • The image includes pig, Ansible, and initialized Pigsty source.

The image build runs these initialization steps:

# Install pig CLI
RUN echo "deb [trusted=yes] https://repo.pigsty.io/apt/infra/ generic main" \
    > /etc/apt/sources.list.d/pigsty.list \
    && apt-get update && apt-get install -y pig

# Initialize Pigsty source and install Ansible
RUN pig sty init -v ${PIGSTY_VERSION} \
    && pig sty boot \
    && pig sty conf -c docker --ip 127.0.0.1

The ./configure -c docker command selects the Docker configuration template. This template uses 127.0.0.1 as the default IP address and applies settings for the container environment.

FAQ

Container won’t start

Make sure that Docker is installed and the host meets the resource requirements. On Docker Desktop, allocate at least 2 GB of memory. Examine ports 2222, 8080, 8443, and 5432 for conflicts.

Can’t access services

Make sure that ./deploy.yml completed successfully. The Web Portal and PostgreSQL require this deployment stage. Run make status to see the service status.

Port conflicts

Change the port in .env or supply an environment variable:

PIGSTY_HTTP_PORT=8888 PIGSTY_PG_PORT=5433 docker compose up -d

Data persistence

The host directory ./data stores persistent container data. To remove this data and start again, use these commands:

make purge        # Remove container and directly delete ./data in the current directory (no countdown)

The purge step deletes the existing data. Back up any required data first.

macOS performance

Docker Desktop on macOS uses a virtual machine. This adds overhead compared with native Linux. Use Docker for development and testing. For production, use native Linux installation.

Domain Access

Point your domain name to the Pigsty server IP address. Set the domain in the home server configuration. This configuration is part of infra_portal:

all:
  vars:
    infra_portal:
      home : { domain: i.pigsty } # Replace i.pigsty with your domain

To use a Let’s Encrypt certificate, also set certbot:

all:
  vars:
    infra_portal:  # domain specifies the domain name  # certbot parameter specifies certificate name
      home : { domain: demo.pigsty.io ,certbot: mycert }

After deployment, run make cert to request the free Let’s Encrypt certificate.

If you omit certbot, Pigsty uses the local certificate authority (CA) to issue an HTTPS certificate. Add the Pigsty CA to your browser trust store before you use that certificate.

You can also configure Nginx to serve local directories or proxy other upstream services. See Nginx Management for the procedure.

4 - Getting Started with PostgreSQL

Connect to PostgreSQL with command-line tools and graphical clients.

PostgreSQL is an open-source relational database. It can store and retrieve different types of data. This guide uses PG as an abbreviation for PostgreSQL.

Use this guide if you know basic Linux commands and want to start with PostgreSQL in Pigsty. The examples use the default single-node installation. For production clusters with multiple nodes, see Service Access.

Basics

The default single-node template creates the pg-meta cluster on the current node. This cluster has one primary instance. PostgreSQL listens on port 5432. The template also creates the meta database.

After installation, close your administration account SSH session. Log in again to load the new environment variables. Enter pp to open psql:

vagrant@pg-meta-1:~$ pp
psql (18.6 (Ubuntu 18.6-1.pgdg24.04+1))
Type "help" for help.

postgres=#

The command uses p as a shortcut for the pig command-line tool. You can also use the postgres operating system account to run psql. This connects to the default postgres administration database.

Connecting to Database

Use a command-line tool or a graphical client to connect. Supply a PostgreSQL connection string in this format:

postgres://username:password@host:port/dbname

Some drivers and clients require separate connection parameters:

ParameterDescriptionExample ValueNotes
hostDatabase server address10.10.10.10Replace with your node IP or domain; can omit for localhost
portPort number5432PG default port, can be omitted
usernameUsernamedbuser_dbaPigsty default database admin
passwordPasswordDBUser.DBAPigsty default admin password (change this!)
dbnameDatabase namemetaDefault template database name

For personal administration, you can use dbuser_dba. This account is a database superuser with full privileges.

If you ran configure -g, the script generated a random administration password. Find the password in ~/pigsty/pigsty.yml:

cat ~/pigsty/pigsty.yml | grep pg_admin_password

Default Accounts

The default single-node template defines these database accounts:

UsernamePasswordRolePurpose
dbuser_dbaDBUser.DBASuperuserDatabase admin (change this!)
dbuser_metaDBUser.MetaBusiness adminApp R/W (change this!)
dbuser_viewDBUser.ViewerRead-only userData viewing (change this!)

These examples connect to the same meta database with different accounts:

postgres://dbuser_dba:DBUser.DBA@10.10.10.10:5432/meta
postgres://dbuser_meta:DBUser.Meta@10.10.10.10:5432/meta
postgres://dbuser_view:DBUser.Viewer@10.10.10.10:5432/meta

Replace the example IP address and password with your actual values. The configure -g command replaces the three example passwords with random passwords. See Security Recommendations for its complete scope and limitations.

Using CLI Tools

psql is the PostgreSQL command-line client. On a Pigsty node, use one of these methods to connect to the local database:

# Simplest way: use postgres system user for local connection (no password needed)
sudo -u postgres psql

# Use connection string (recommended, most universal)
psql 'postgres://dbuser_dba:DBUser.DBA@10.10.10.10:5432/meta'

# Use parameter form
psql -h 10.10.10.10 -p 5432 -U dbuser_dba -d meta

# Use env vars to avoid password appearing in command line
export PGPASSWORD='DBUser.DBA'
psql -h 10.10.10.10 -p 5432 -U dbuser_dba -d meta

Replace the example IP address and password before you run the connection commands. After a successful connection, psql shows a prompt:

psql (18.6)
Type "help" for help.

meta=#

SQL example

End each SQL statement with a semicolon (;). This example creates a test table, adds two rows, queries the rows, and removes the table:

-- Check PostgreSQL version
SELECT version();

-- Check current time
SELECT now();

-- Create a test table
CREATE TABLE test (id SERIAL PRIMARY KEY, name TEXT, created_at TIMESTAMPTZ DEFAULT now());

-- Insert data
INSERT INTO test (name) VALUES ('hello'), ('world');

-- Query data
SELECT * FROM test;

-- Drop test table
DROP TABLE test;

Using Graphical Clients

You can also connect with a graphical client.

Grafana

The INFRA module includes Grafana and a PostgreSQL data source named Meta. Open the Web UI. Use the Grafana Explore panel to query PostgreSQL with SQL. This method requires no additional client software.

The default Grafana username is admin. Find its password in grafana_admin_password in the inventory. The default password is pigsty.

DataGrip

DataGrip is a database development tool from JetBrains. IntelliJ IDEA also has a Database Console that can connect to PostgreSQL.

DBeaver

DBeaver is a free, open-source database client. It runs on multiple desktop operating systems and supports PostgreSQL and other databases.

pgAdmin

pgAdmin is a PostgreSQL administration client from PGDG. You can use its browser interface or desktop application. Pigsty supplies a pgAdmin template for deployment with Docker.

Viewing Monitoring Dashboards

Pigsty supplies PostgreSQL monitoring dashboards. They show information from cluster summaries to individual tables.

Open PGSQL Overview first. Select a cluster to see its instances and databases. Use the dashboard links to examine tables, indexes, and functions.

Trying Extensions

PostgreSQL extensions add data types, functions, index methods, and other database features. Pigsty packages 600 extensions in 16 categories. These categories include time-series data, geographic data, vectors, and full-text search.

Start with these extensions:

  • postgis processes geographic and location data. The default template installs it.
  • pgvector supplies vector similarity search for AI embeddings. The default template installs it.
  • timescaledb stores and queries time-series data. Install it when required.

Use these commands to list and enable extensions:

\dx                            -- psql meta command, list installed extensions
TABLE pg_available_extensions; -- Query installed, available extensions
CREATE EXTENSION postgis;      -- Enable postgis extension

5 - Customize Pigsty with Configuration

Define nodes, modules, databases, and users in the Pigsty inventory.

You can generate a configuration file with the configuration wizard. You can also write the file yourself. This guide builds an inventory in stages.

The deploy.yml playbook deploys NODE, INFRA, ETCD, MINIO, and PGSQL when the inventory defines them. Docker, Redis, Kafka, native MySQL, JUICE, and VIBE require their own playbooks. The procedures below show the configuration and playbooks for each stage.

Minimal Configuration

The smallest valid configuration defines admin_ip. This is the IP address of the administration node where you installed Pigsty:

Minimal
all: { vars: { admin_ip: 10.10.10.10 } }
Mirror
# Set region: china to use mirrors
all: { vars: { admin_ip: 10.10.10.10, region: china } }

This inventory defines no deployment targets. With this configuration, ./deploy.yml generates a self-signed certificate authority (CA) in files/pki/ca. The CA issues certificates for the deployment.

Set region to select a software repository region. The available values are default, china, and europe.

Add Nodes

The NODE module manages the nodes in the inventory. Add a node IP address to include that node in NODE module deployment:

Minimal
all:  # Remember to replace 10.10.10.10 with your actual IP
  children: { nodes: { hosts: { 10.10.10.10: {} } } }
  vars:
    admin_ip: 10.10.10.10                   # Current node IP
    region: default                         # Default repos
    node_repo_modules: node,pgsql,infra     # Add node, pgsql, infra repos
Mirror
all:  # Remember to replace 10.10.10.10 with your actual IP
  children: { nodes: { hosts: { 10.10.10.10: {} } } }
  vars:

Define Databases and Users

Define PostgreSQL databases and users in the inventory:

all:
  children:
    # Other groups and variables hidden for brevity
    pg-meta:
      hosts: { 10.10.10.10: { pg_seq: 1, pg_role: primary } }
      vars:
        pg_cluster: pg-meta
        pg_users:       # Define database users
          - { name: dbuser_meta ,password: DBUser.Meta ,pgbouncer: true ,roles: [dbrole_admin] ,comment: admin user  }
        pg_databases:   # Define business databases
          - { name: meta ,baseline: cmdb.sql ,comment: pigsty meta database ,schemas: [pigsty] ,extensions: [vector] }

pg_users defines the dbuser_meta account with the example password DBUser.Meta. pg_databases defines the meta database with the vector extension. It also loads the optional Pigsty CMDB schema. Replace the example password before deployment.

Configure PG Version and Extensions

Pigsty supports multiple PostgreSQL major versions and 600 extensions. The example below replaces PostgreSQL 18 with PostgreSQL 16. This procedure recreates pg-meta; it is not an in-place version change.

Before removal, back up the cluster and confirm the target. Use check mode to examine the removal tasks:

./pgsql-rm.yml -l pg-meta --check # Preflight old pg-meta removal; execute only after backup and target confirmation

The --check command does not perform the removal. Complete the required removal before you recreate the cluster.

Set these parameters in the new configuration:

  • pg_extensions installs timescaledb, postgis, and pgvector packages.
  • pg_libs loads the timescaledb, pg_stat_statements, and auto_explain libraries.
  • pg_databases enables vector, postgis, and timescaledb in the meta database.
all:
  children:
    infra:   { hosts: { 10.10.10.10: { infra_seq: 1 } } }
    etcd:    { hosts: { 10.10.10.10: { etcd_seq:  1 } } } # Add etcd cluster
    pg-meta:
      hosts: { 10.10.10.10: { pg_seq: 1, pg_role: primary } }
      vars:
        pg_cluster: pg-meta
        pg_version: 16   # Specify PG version as 16
        pg_extensions: [ timescaledb, postgis, pgvector ]      # Install these extensions
        pg_libs: 'timescaledb,pg_stat_statements,auto_explain'  # Preload these extension libraries
        pg_databases: [ { name: meta ,baseline: cmdb.sql ,comment: pigsty meta database ,schemas: [pigsty] ,extensions: [vector, postgis, timescaledb ] } ]
        pg_users: [ { name: dbuser_meta ,password: DBUser.Meta ,pgbouncer: true ,roles: [dbrole_admin] ,comment: admin user } ]

  vars:
    admin_ip: 10.10.10.10
    region: default
    node_repo_modules: node,pgsql,infra

7 - Offline Installation

Install Pigsty without Internet access. Use or build offline packages.

Pigsty normally installs packages from upstream Internet repositories. If the environment has no Internet access, use offline packages.

Overview

An offline package contains the RPM or DEB packages and dependencies from a local APT or YUM repository. It records the repository contents after an online installation.

Use offline packages for production deployments when you need consistent package versions. They let new nodes use the same packages as the existing nodes. They also remove the installation dependency on upstream repository availability.

Advantages
  • Install in environments without Internet access.
  • Download packages in advance to reduce installation time.
  • Avoid installation failures from later upstream dependency changes.
  • Download each package once for multiple nodes.
  • Use one local repository to control package versions across nodes.
Limitations

Offline packages target specific operating system minor versions. A package can fail on a different version. Its contents reflect the creation date and can omit later updates or security patches. An offline package is approximately 1 GB. Online installation downloads only the packages that you need.

Using Offline Packages

Do these steps in order:

  2. Download and extract the Pigsty source package into your home directory.
  3. Run cd ~/pigsty to enter the source directory.
  4. Run ./bootstrap to extract the offline package, configure the local repository, and install Ansible.
  5. Run ./configure -g -c rich to select the rich template and generate random passwords.
  6. Run ./deploy.yml to install the core modules from the local repository.

You can also use your own configuration with the repository settings below. Other optional modules still require their own playbooks.

demo/install-offline.cast — /demo/install-offline.cast

Package error after an earlier installation failure

The error No package nginx available usually follows an incomplete installation attempt. The documented recovery removes /www/pigsty and runs deployment again. Before removal, make sure that the directory contains only the repository that you intend to rebuild.

To use an extracted offline package with your own configuration, set these parameters:

  • Set repo_enabled to true to enable the local software repository.
  • Set node_repo_modules to local to install all packages from that repository.

Most templates disable repository creation and select node,infra,pgsql as upstream package sources. With node_repo_modules: local, the local repository is the only package source. To permit upstream repositories as well, use local,node,infra,pgsql.

Hybrid installation

If the environment has Internet access, you can combine local and upstream package sources. Use the offline package as the initial repository. Then download missing packages from upstream.

For example, the v4.5.0 EL 9 package targets Rocky Linux 9.8. If you use Rocky Linux 9.6, run make repo-build before deployment to download the packages required for 9.6. This hybrid method requires Internet access to the upstream repositories.

Making Offline Packages

To build a package for another operating system, use the cache.yml playbook.

  1. Select an online node with the exact operating system version and architecture of the offline nodes.
  2. Run ./configure -c rich and complete an online installation with the rich template.
  3. Make sure that the target INFRA node has a local repository at /www/pigsty.
  4. If the repository is absent, run ./infra.yml -t repo against that node first.
  5. From ~/pigsty, run ./cache.yml -l <infra-host> to build and fetch the package from one INFRA node.
  6. Copy the package to the offline environment with FTP, SCP, or a USB device.
  7. Use bootstrap to extract the package.

Bootstrap

Pigsty uses Ansible to run playbooks. The bootstrap script installs Ansible and prepares the required package repositories:

./bootstrap       # Ensure ansible is correctly installed (if offline package exists, use offline installation and extract first)

Run bootstrap in these cases:

  • You downloaded or cloned the source manually and Ansible is absent.
  • You need to extract an offline package and install Ansible from it.

By default, the script looks for /tmp/pkg.tgz. Use -p to specify a different package path. If the package exists, the script extracts it and installs Ansible from the local repository. If the package is absent, the script attempts an online Ansible installation. If that installation fails, install Ansible manually.

Bootstrap moves existing repository files

By default, bootstrap moves existing repository configurations into a backup directory. This leaves only the required repositories enabled. On EL, the backup directory is /etc/yum.repos.d/backup. On Debian and Ubuntu, it is /etc/apt/backup.

To keep existing repository configurations, use -k|--keep:

./bootstrap -k # or --keep

8 - Slim Installation

Install PostgreSQL clusters without the monitoring infrastructure.

Use Slim Installation to deploy PostgreSQL without the monitoring infrastructure. It installs ETCD, PGSQL, and part of NODE. It does not install INFRA, monitoring services, or a local software repository.

When to use Slim Installation
  • You only need PostgreSQL.
  • You have limited CPU or memory resources.
  • You already have an external monitoring system.
  • You do not need Grafana dashboards.

On one node, the omitted infrastructure uses approximately 0.2 vCPU and 500 MB of memory.

Installation limits

The Web UI and local software repository require INFRA. Slim Installation does not supply these features. Offline installation supports only one node in this mode. For multiple nodes, Slim Installation requires online package access.

Overview

  1. Download Pigsty and enter the source directory.
  2. Select the slim configuration template with ./configure -g -c slim.
  3. Run ./slim.yml instead of ./deploy.yml.
curl https://repo.pigsty.io/get | bash
cd ~/pigsty
./configure -g -c slim
./slim.yml

Description

Slim Installation configures these components:

ComponentRequiredDescription
patroni⚠️ RequiredBootstrap HA PostgreSQL cluster
etcd⚠️ RequiredMeta database dependency (DCS) for Patroni
pgbouncer✔️ OptionalPostgreSQL connection pooler
vip-manager✔️ OptionalL2 VIP binding to PostgreSQL cluster primary
haproxy✔️ OptionalAuto-routing services via Patroni health checks
chronyd✔️ OptionalTime synchronization with NTP server
tuned✔️ OptionalNode tuning template and kernel parameter management

You can disable all optional components through the configuration. Patroni and etcd remain required.

Without INFRA, Nginx does not serve a local software repository to other nodes. Thus, offline Slim Installation supports only one node.

9 - Security Recommendations

Protect credentials, restrict network access, and control access to sensitive files.

The default configuration supports local demonstrations and development on a trusted intranet. If other hosts can reach the deployment, examine the credentials, network access, and sensitive files.

For production, also review the Security Model, Compliance, and Security Considerations.

Passwords

Pigsty publishes its default credentials in the source code and documentation. Do not use these credentials in production.

Run the configuration wizard with -g to generate random passwords:

./configure -g

The wizard replaces the built-in parameters and example credentials that it recognizes. It does not replace these credentials:

  • The pgBackRest cipher_pass.
  • Silo user passwords and selected example passwords in ha/safe.
  • Database, object-storage, or application credentials that you added yourself.

After generation, examine pigsty.yml. Replace every credential that the wizard did not change.

The wizard prints generated passwords to the terminal. Protect terminal records and automation logs that contain these passwords. See the Default Credentials Checklist for the complete scope.

Firewall

The default value of node_firewall_mode is zone. This mode trusts the intranet defined by node_firewall_intranet. It restricts access to ports from public networks.

PortServicePublic by Default
22SSHYes
80Nginx HTTPYes
443Nginx HTTPSYes
5432PostgreSQLNot in the base default; exposed additionally by the demo pigsty.yml

For production, normally remove port 5432 from the demonstration configuration. If applications require direct database access, permit only their source addresses. Apply these restrictions in the cloud security group, host firewall, and PostgreSQL HBA rules.

Make sure that the intranet definition matches your trusted network. The default RFC 1918 address ranges can include networks that you do not trust. Do not automatically trust office networks, container networks, or other tenant networks.

Files

These files and directories contain sensitive information:

File or directoryContents
pigsty.ymlSystem and application credentials, node definitions, and service configuration
files/pki/ca/ca.keyLocal CA private key
Administration account SSH private keyAccess credentials for managed nodes
files/pki/misc/*.keyClient-certificate private keys
/pg/tmp/pg-user-*.sqlSQL files with plaintext passwords from user creation

Restrict access to the administration node and configuration repository. Do not commit complete inventories or private keys to public repositories. Keep controlled backups of the CA private key and required configuration.
