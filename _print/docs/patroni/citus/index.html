Citus support

Patroni integration details for Citus coordinator and worker groups.

Source: https://patroni.readthedocs.io/en/latest/citus.html

Patroni automates deployment of Multi-Node Citus clusters.

TL;DR

Apply these rules:

  1. Install the Citus PostgreSQL extension on every node. The minimum supported version is 10.0. We recommend at least 11.2 for transparent worker switchovers and restarts.
  2. Use the same cluster name (scope) on all Citus nodes.
  3. Use the same superuser credentials on the coordinator and all workers. Configure pg_hba.conf to permit superuser access between all nodes.
  4. Permit worker access to the coordinator REST API. Use the same credentials. If client certificates are configured, the coordinator must accept worker certificates.
  5. Add this section to patroni.yaml:
citus:
  group: X  # 0 for coordinator and 1, 2, 3, etc for workers
  database: citus  # must be the same on all nodes

Then start Patroni. It performs these operations:

  1. Set bootstrap.dcs.synchronous_mode to quorum, unless you explicitly set another value.
  2. Add the citus extension to shared_preload_libraries.
  3. Set max_prepared_transactions to 2*max_connections, unless it is explicitly set in dynamic configuration.
  4. Change citus.local_hostname from localhost to the address Patroni uses for local PostgreSQL connections. PostgreSQL might not listen on localhost.
  5. Create citus.database, then run CREATE EXTENSION citus.
  6. Add current superuser credentials to pg_dist_authinfo for cross-node communication. Update them if you later change the superuser username, password, sslcert, or sslkey.
  7. On the coordinator primary, discover worker primaries and add them to pg_dist_node with citus_add_node().
  8. Maintain pg_dist_node after failover or switchover in coordinator or worker clusters.

patronictl

Coordinator and worker clusters are separate PostgreSQL/Patroni clusters. Citus groups them logically. Most operations therefore cannot manage them as one entity.

A citus section in patroni.yaml changes patronictl behavior in two ways:

  1. By default, list and topology show all coordinators and workers in the Citus formation. The Group column identifies their Citus groups.
  2. patronictl commands accept --group. Some use a default from patroni.yaml. For example, patronictl_pause defaults to group in the citus section. patronictl_switchover and patronictl_remove require an explicit group.

Citus worker switchover

Citus can make an orchestrated worker switchover nearly transparent to applications. Applications connect to the coordinator, which connects to workers. Citus can pause coordinator SQL traffic for the shards on the affected worker. The coordinator holds this traffic during switchover. Traffic resumes when the new worker primary can accept read/write queries.

# The old worker primary is assigned as a secondary.

# The future worker primary notifies the coordinator that it acquired the leader lock in DCS and about to run "pg_ctl promote".

2024-08-26 07:02:41,485 DEBUG: query(COMMIT, ())
# From this moment the application traffic on the coordinator to the worker group 2 is unblocked.

Secondary nodes

Since Patroni v4.0.0, Citus secondary nodes without the noloadbalance tag are also registered in pg_dist_node. To use them for read-only queries, applications must change citus.use_secondary_nodes.

Peek into DCS

The Citus cluster (coordinator and workers) are stored in DCS as a fleet of Patroni clusters logically grouped together:

/service/batman/              # scope=batman
/service/batman/0/            # citus.group=0, coordinator
/service/batman/0/initialize
/service/batman/0/leader
/service/batman/0/members/
/service/batman/0/members/m1
/service/batman/0/members/m2
/service/batman/1/            # citus.group=1, worker
/service/batman/1/initialize
/service/batman/1/leader
/service/batman/1/members/
/service/batman/1/members/m3
/service/batman/1/members/m4
...

Most DCS implementations can read the whole Citus cluster with one recursive request using this structure. Only coordinators read the whole tree, to discover workers. Workers read their own group subtree and, in some cases, the coordinator subtree.

Citus on Kubernetes

Kubernetes does not support hierarchical structures. Patroni therefore includes the Citus group in every Kubernetes object name:

batman-0-leader  # the leader config map for the coordinator
batman-0-config  # the config map holding initialize, config, and history "keys"
...
batman-1-leader  # the leader config map for worker group 1
batman-1-config
...

The naming pattern is ${scope}-${citus.group}-${type}.

Patroni discovers Kubernetes objects with a label selector. All Patroni/Citus Pods and Endpoints/ConfigMaps must have matching labels. Configure Patroni to use these labels through Kubernetes settings or environment variables <kubernetes_environment>.

A couple of examples of Patroni configuration using Pods environment variables:

  1. for the coordinator cluster
apiVersion: v1
kind: Pod
metadata:
  labels:
    application: patroni
    citus-group: "0"
    citus-type: coordinator
    cluster-name: citusdemo
  name: citusdemo-0-0
  namespace: default
spec:
  containers:
  - env:
    - name: PATRONI_SCOPE
      value: citusdemo
    - name: PATRONI_NAME
      valueFrom:
        fieldRef:
          apiVersion: v1
          fieldPath: metadata.name
    - name: PATRONI_KUBERNETES_POD_IP
      valueFrom:
        fieldRef:
          apiVersion: v1
          fieldPath: status.podIP
    - name: PATRONI_KUBERNETES_NAMESPACE
      valueFrom:
        fieldRef:
          apiVersion: v1
          fieldPath: metadata.namespace
    - name: PATRONI_KUBERNETES_LABELS
      value: '{application: patroni}'
    - name: PATRONI_CITUS_DATABASE
      value: citus
    - name: PATRONI_CITUS_GROUP
      value: "0"
  1. for the worker cluster from the group 2
apiVersion: v1
kind: Pod
metadata:
  labels:
    application: patroni
    citus-group: "2"
    citus-type: worker
    cluster-name: citusdemo
  name: citusdemo-2-0
  namespace: default
spec:
  containers:
  - env:
    - name: PATRONI_SCOPE
      value: citusdemo
    - name: PATRONI_NAME
      valueFrom:
        fieldRef:
          apiVersion: v1
          fieldPath: metadata.name
    - name: PATRONI_KUBERNETES_POD_IP
      valueFrom:
        fieldRef:
          apiVersion: v1
          fieldPath: status.podIP
    - name: PATRONI_KUBERNETES_NAMESPACE
      valueFrom:
        fieldRef:
          apiVersion: v1
          fieldPath: metadata.namespace
    - name: PATRONI_KUBERNETES_LABELS
      value: '{application: patroni}'
    - name: PATRONI_CITUS_DATABASE
      value: citus
    - name: PATRONI_CITUS_GROUP
      value: "2"

Both examples set the citus-group label to identify the object’s Citus group. They set PATRONI_CITUS_GROUP to the same value. Patroni automatically adds citus-group: ${env.PATRONI_CITUS_GROUP} to new ConfigMaps and Endpoints:

apiVersion: v1
kind: ConfigMap
metadata:
  name: citusdemo-0-leader  # Is generated as ${env.PATRONI_SCOPE}-${env.PATRONI_CITUS_GROUP}-leader
  labels:
    application: patroni    # Is set from the ${env.PATRONI_KUBERNETES_LABELS}
    cluster-name: citusdemo # Is automatically set from the ${env.PATRONI_SCOPE}
    citus-group: '0'        # Is automatically set from the ${env.PATRONI_CITUS_GROUP}

Citus upgrades and PostgreSQL major upgrades

Read the Citus upgrade documentation. One change applies: restart PostgreSQL with patronictl_restart instead of systemctl restart.

A PostgreSQL major upgrade with Citus requires both projects’ upgrade procedures. Combine the Citus major upgrade documentation with Patroni PostgreSQL major upgrade<major_upgrade> instructions. A Citus formation contains multiple Patroni clusters: the coordinator and workers. Upgrade each cluster independently.
