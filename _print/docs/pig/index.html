1 - Getting Started

Install PostgreSQL and pgvector, start an instance, and enable the extension

This tutorial installs PostgreSQL 18 and pgvector, starts a local test instance, and enables the extension in a database.

Use a supported Linux test host with internet access and curl installed. You need root or sudo access. Run the commands in order.

Install PIG

curl -fsSL https://repo.pigsty.io/pig | bash
pig version

In mainland China, use https://repo.pigsty.cc/pig instead. The installer selects the RPM or DEB package for your host. See Installation for other methods.

Check the host

pig status

Check the OS code, architecture, and detected PostgreSQL installations. This command also tests repository connectivity.

Add repositories

Add PGDG and Pigsty PostgreSQL repositories, then refresh package metadata:

sudo pig repo add pgsql --update

For China mirrors, add --mirror to this command.

Install PostgreSQL and pgvector

sudo pig install -v 18 pg18 vector

Review the package manager’s transaction and confirm it.

pg18 selects the PostgreSQL 18 packages. vector selects pgvector. The -v 18 option selects the extension’s PostgreSQL major version.

Check the installed extension files:

pig ext status -v 18

Start a test instance

This tutorial uses /pg/data-demo and port 15432 to avoid the default cluster on port 5432. Use an unused directory and port.

Create an empty data directory owned by the postgres operating-system user:

sudo install -d -m 700 -o postgres -g postgres /pg/data-demo
sudo pig pg init -v 18 -D /pg/data-demo

Start the instance on port 15432:

sudo pig pg start -v 18 -D /pg/data-demo -O '-p 15432'
sudo pig pg status -v 18 -D /pg/data-demo

Enable and test pgvector

Connect to the test instance:

sudo pig pg psql -v 18 -D /pg/data-demo

PIG reads the instance’s connection information from the specified data directory. At the psql prompt, run:

CREATE EXTENSION vector;
SELECT extname, extversion FROM pg_extension WHERE extname = 'vector';
SELECT '[1,2,3]'::vector <-> '[4,5,6]'::vector AS distance;

The first query returns the installed pgvector version. The second returns a distance of approximately 5.196. Exit psql with \q.

CREATE EXTENSION enables an extension in the connected database. Repeat it in each database that needs pgvector.

Stop the test instance when you finish:

sudo pig pg stop -v 18 -D /pg/data-demo

The data stays in /pg/data-demo. Run the start command again to reuse the instance. See PostgreSQL management for service configuration and other operations.

Find more extensions

pig ext list                 # List the catalog
pig ext list duckdb          # Search by name or description
pig ext info pg_duckdb       # Show metadata and setup requirements
pig ext avail pg_duckdb      # Show package availability

Before installing another extension, use info to check its setup requirements and avail to check package availability.

Select packages and versions

To use another PostgreSQL major version, replace 18 in the commands above. See extension installation for package groups, version selection, and existing installations.

Inspect and update

pig ext status -v 18 lists installed extension files. To list extensions enabled in a database, run \dx in psql. See extension updates when you need to upgrade a package and its database objects.

2 - Introduction

What PIG does, how package installation works, and which platforms it supports

PIG is a command-line tool for installing and managing PostgreSQL and its extensions. It maps extension names to RPM or DEB packages and uses apt, dnf, or yum to install them.

The catalog contains 616 extension entries. PIG selects package names for your PostgreSQL major version, operating system, and CPU architecture. It also provides commands for source builds, local PostgreSQL operations, backups, and Pigsty administration.

How package installation works

For example, this command installs pgvector for PostgreSQL 18:

sudo pig install vector -v 18

PIG resolves vector to pgvector_18 on EL or postgresql-18-pgvector on Debian and Ubuntu. The system package manager resolves dependencies and installs the files.

To enable the extension, connect to the intended database and run:

CREATE EXTENSION vector;

Some extensions also need a setting in shared_preload_libraries and a PostgreSQL restart. Use pig ext info NAME to check these requirements. See package and database operations for updates and removal.

PIG is needed only when you run its commands. PostgreSQL and installed extensions continue to work without it. You can also use the Pigsty repositories directly with apt or dnf.

Choose a workflow

  • Use an existing host: add repositories with pig repo add pgsql -u, then install the required packages.
  • Configure all repositories on a new host: use pig repo set. It backs up and replaces the existing repository definitions.
  • Build a package: prepare a build host and use the maintained specifications with pig build.
  • Prepare an offline installation: collect packages with pig ext import, index them with pig repo create, and archive them with pig repo cache. See offline repositories.
  • Write a script or agent workflow: inspect pig -o json --help and use the supported output and plan options in the command reference.

3 - Installation

How to download and install the pig package manager

Install PIG with the Linux installer, a system package, or a release archive. The current version is v1.10.2. The download page lists all release files.

Script installation

On Linux, run:

curl -fsSL https://repo.pigsty.io/pig | bash

In mainland China, use:

curl -fsSL https://repo.pigsty.cc/pig | bash

The script detects the architecture, downloads the RPM or DEB package, and installs it with rpm or dpkg. Installation requires root or sudo access.

Check the installed version:

pig version

To select a published version, pass its version number:

curl -fsSL https://repo.pigsty.io/pig | bash -s 1.10.2

Download release artifacts

Choose a file for your operating system and architecture on the download page or GitHub release.

For a release archive, extract it and install the pig executable in a directory on your PATH. For example, on Apple Silicon:

curl -fLO https://github.com/pgsty/pig/releases/download/v1.10.2/pig-v1.10.2.darwin-arm64.tar.gz
tar -xzf pig-v1.10.2.darwin-arm64.tar.gz
sudo mkdir -p /usr/local/bin
sudo install -m 0755 pig /usr/local/bin/pig
pig version

The release includes SHA-256 checksums. Use sha256sum on Linux or shasum -a 256 on macOS to compare your downloaded file with its listed hash.

The macOS binary supports catalog queries, inventory editing, and other commands that do not need Linux package managers. Install PostgreSQL packages on a supported Linux host.

Repository installation

To manage PIG with the system package manager, add the Pigsty Infra repository. Choose the tab for your host:

APT (Debian / Ubuntu)
sudo tee /etc/apt/sources.list.d/pigsty-infra.list > /dev/null <<EOF
deb [trusted=yes] https://repo.pigsty.io/apt/infra generic main
EOF

sudo apt update
sudo apt install -y pig
DNF (EL)
sudo tee /etc/yum.repos.d/pigsty-infra.repo > /dev/null <<-'EOF'
[pigsty-infra]
name=Pigsty Infra for $basearch
baseurl=https://repo.pigsty.io/yum/infra/$basearch
enabled=1
gpgcheck=0
module_hotfixes=1
EOF

sudo dnf makecache
sudo dnf install -y pig

These definitions disable signature checks for the Pigsty repository. For key handling and verification settings, see repository keys.

Update

On Linux, update the executable with:

sudo pig update

Use -m for the China mirror or -v 1.10.2 to select that version. For an archive installation on macOS, download the new archive and replace the installed executable.

Refresh the extension catalog separately:

pig ext reload

This updates catalog metadata, leaving installed packages unchanged.

Uninstall

Choose the command that matches your installation:

sudo apt remove pig              # Debian / Ubuntu package
sudo dnf remove pig              # EL package
sudo rm /usr/local/bin/pig        # Archive installed at this path

If you installed the archive elsewhere, remove that executable instead. PostgreSQL and its extensions continue to run without PIG.

Build from source

Install Git, Make, and the Go toolchain specified in the project’s go.mod. Build the current release:

git clone --branch v1.10.2 https://github.com/pgsty/pig.git
cd pig
go mod download
make build
./pig version

make build produces ./pig for the current platform. The release workflow uses GoReleaser to produce RPM, DEB, and tar.gz files.

Continue with Getting started to install PostgreSQL and enable an extension.

v1.10.0

Pig v1.10.0 strengthens the correctness and safety of existing commands. It verifies PostgreSQL targets before operations, preserves Inventory sources and YAML types, and makes repository, extension, and automation results match the work actually performed. The bundled catalog grows from 600 to 603 records. Embedded Pigsty remains 4.5.0; the default cargo-pgrx remains 0.19.3.

PostgreSQL targets and maintenance

  • An explicit -D binds psql, ps, kill, vacuum, analyze, freeze, and repack to the selected instance, including --all database enumeration. PIG validates the PID, data directory, port, socket, and process identity before starting the SQL client. Invalid, stale, copied, or uncertain runtime metadata causes failure instead of a fallback to another instance.
  • Without -D, those SQL commands retain native client connection defaults. pg clone and pg fork retain their own port options. Promotion timeline checks use the selected instance or its control data; an unresolved timeline is left unknown.
  • Plans and confirmation retry commands preserve the selected data directory, PostgreSQL version, operating-system user, and maintenance options. VACUUM FULL plans correctly require confirmation.
  • Maintenance operands are literal database names. Values containing = or beginning with postgres:// or postgresql:// are rejected before planning or execution, without echoing the value. Spaces and non-ASCII names remain supported. Generated commands put names after --, so a database named --all cannot become a command option.
  • vacuum, analyze, and freeze --all validate the complete database list before maintenance begins. Use native clients when a connection string or a database name rejected by this boundary is required.

See pig pg for target selection and maintenance commands for database-name rules.

Runtime state, recovery, and fork safety

  • Permission failures, malformed PID metadata, and unavailable process identity are reported as errors or unknown state. They cannot authorize forced initialization, restore, or fork replacement. pg status returns 130201 (exit 3) for permission failures and 130808 (exit 1) for other runtime-probe failures. Plans report an unresolved precondition as unknown.
  • Declining PITR confirmation or reaching EOF returns 161001 (exit 7) before any service stop, restore, or startup. An unknown state cannot supply a PID for forced termination or count as successful startup. Post-restore SQL checks require a verified target.
  • Replacing a nonempty unmanaged fork requires valid ownership metadata with a matching explicit target path. Missing, damaged, or mismatched metadata cannot authorize deletion. Existing protections for running targets and source/destination relationships remain in force.
  • Clone and fork path checks run as the selected database operating-system user when needed, supporting private 0700 data directories. An inaccessible or unresolved path cannot bypass validation. Managed orphan cleanup remains available through the managed fork name.
  • Files written as the database user use private sibling staging and exact-target replacement. The new file has 0600 permissions; directory or symlink targets are refused, and replacement does not overwrite the contents of another hard link to the old file.

The PITR reference explains the managed recovery workflow; pig pb restore remains a separate restore primitive.

Inventory and Pigsty

  • sty deploy and do pass the resolved Inventory path explicitly to Ansible. Flag and environment paths resolve from the caller’s working directory; quoted ~/ paths expand before resolution. A selected missing or invalid source does not silently fall back to another inventory.
  • pg_users[].roles preserves both role-name strings and structured grants, including grant state and optional admin, set, and inherit attributes.
  • Editing, serialization, and CMDB export retain strings that YAML consumers might otherwise interpret as numbers, dates, or timestamps. Existing timestamp scalars retain their original source representation. Independent PyYAML checks verify the emitted string types.

It improves the reliability of the pig build pipeline and extends catalog and alias coverage. Total extensions increase from 451 to 461.

Highlights

  • Build source download improvements (pig build get):
    • Parse multi-source Source fields (whitespace/newline/tab) and deduplicate entries.
    • Add source mappings for agensgraph / agentsgraph.
    • pgedge now downloads both postgresql-17.9.tar.gz and spock-5.0.5.tar.gz.
  • Dependency resolution and install improvements (pig build dep):
    • RPM dependencies can infer the PG major version from pgmajorversion in spec files. Missing spec/control files return explicit errors.
    • DEB dependency parsing now covers Build-Depends / Build-Depends-Arch / Build-Depends-Indep, including multiline fields, alternatives, arch qualifiers, and build-profile cleanup.
    • PGVERSION placeholders can be expanded from --pg, installed PG majors, or extension metadata.
    • Dependency install failures are downgraded to warnings so batch runs continue.
  • DEB build result semantics fixed (pig build ext/pkg):
    • A successful build command exit code determines success. Artifact discovery is best-effort and can only produce warnings.
    • Suppress empty package-list banners on successful no-artifact runs.
    • Partial artifacts are warnings, not failures.
    • Build logs now print real metadata source/version values instead of always composing name-version.
  • Better machine-readable ext operation output (pig ext rm/update):
    • After alias resolution, removed/updated now returns resolved package names instead of extension aliases.
  • Extension catalog and alias updates:
    • New aliases: agensgraph / agens, pgedge, babelfishpg.
    • openhalodb is aligned to PG14 package naming; ivorysqldb naming is aligned.
    • Fork metadata and availability matrix were refreshed in batch (including timescaledb, pgmq, orioledb, documentdb, pg_tde, and babelfishpg_* entries).
  • Engineering and release:
    • Updated the version to v1.3.0, including a v1.2.1 transition commit. Changed the copyright year to 2026. Updated the README for 461 extensions and current alias documentation.

Compatibility Notes

  • Structured removed/updated fields in pig ext rm/update now contain package names. Automation that matched extension aliases should update parsing logic.

v1.1.0

This release upgrades the CLI architecture from v1.0.0 to v1.1.0, with 79 commits across 193 changed files. It extends pig from an interactive CLI to a CLI that agents can orchestrate.

Seven new extensions are added, bringing the total available extensions to 451.

New Features

  • Adds a unified output framework for agents. Global --output supports text/yaml/json/json-pretty. A common Result structure provides stable status codes and machine-readable output for ext/repo/pg/pt/pb/pitr/status/version/context.
  • Adds ANCS (Agent Native Command Schema) metadata, including type/volatility/parallel/risk/confirm/os_user/cost fields. In structured mode, help outputs a command capability tree. Agents can use it to identify capabilities and risks.
  • Adds the pig context (pig ctx) environment snapshot command. One call collects host, PostgreSQL, Patroni, pgBackRest, and extension information for direct use in agent workflows.
  • Extends plan support beyond PITR with pig ext add/rm --plan, pig pg stop/restart --plan, and pig pt switchover/failover --plan. These match pig pitr --plan/--dry-run in a common, reviewable format. Plans show actions, scope, risks, and expected results.
  • Extends structured results with native pgbackrest info JSON. Unifies structured return DTOs across Patroni/PostgreSQL/PITR/Repo/Ext for automation compatibility.
  • Adds legacy structured wrappers for command groups such as pg_exporter/pg_probe/do/sty. These retain existing interaction behavior while providing structured execution results and captured output.
  • Update pigsty to v4.1.0.

v1.0.0

This release adds three command groups: pig pg for PostgreSQL, pig pt for Patroni, and pig pb for pgBackRest. It also adds a coordinated PITR command and improves extension availability displays.

New Commands

  • pig pg - PostgreSQL instance management

    • pg init/start/stop/restart/reload/status - Control and manage PostgreSQL instances
    • pg role/promote - Detect and switch instance role (primary/replica)
    • pg psql/ps/kill - Connection and session management
    • pg vacuum/analyze/freeze/repack - Database maintenance operations
    • pg log - Log viewing (list/tail/cat/less)

  • pig pt - Patroni cluster management

    • pt list/config - View cluster status and configuration
    • pt restart/reload/reinit - Manage cluster members
    • pt switchover/failover - Cluster failover operations
    • pt pause/resume - Control automatic failover
    • pt start/stop/status/log - Patroni service management

  • pig pb - pgBackRest backup management

    • pb info/ls - View backup information
    • pb backup/restore/expire - Backup operations
    • pb create/upgrade/delete - Stanza management
    • pb check/start/stop/log - Control operations

  • pig pitr - Orchestrated Point-In-Time Recovery

    • Automatic Patroni/PostgreSQL coordination
    • Multiple recovery targets: time, LSN, XID, restore point
    • Dry-run mode and post-recovery guidance

New Features

  • Add availability matrix to pig ext avail and pig ext ls

Improvements

  • Unified command aliases across pg/pt/pb commands
  • Standardized error message format
  • Code refactoring and cleanup

pig CLI command reference overview

pig manages PostgreSQL packages, local database services, and Pigsty deployments. Choose a command below for your task. Use pig COMMAND --help to see the options supported by your installed program.

  • pig repo: manage software repositories
  • pig ext: manage PostgreSQL extensions
  • pig build: build extensions from source
  • pig install: install packages with the native package manager and translate PostgreSQL aliases
  • pig sty: manage Pigsty installation and Grafana dashboards
  • pig inventory: inspect, edit, validate, and exchange the Pigsty inventory
  • pig do: run Pigsty administration playbook tasks
  • pig pe: access pg_exporter metrics and configuration
  • pig pg: manage local PostgreSQL servers
  • pig pt: run patronictl transparently with service and config helpers
  • pig pb: manage pgBackRest backup and restore
  • pig pitr: run the full PITR workflow
  • pig context: output an environment context snapshot for humans and agents
  • pig license: issue and verify Pigsty licenses
  • pig status / update / version: inspect environment status, upgrade pig, and print version information

Global options

OptionPurpose
-h, --helpShow help
-H, --home PATHSelect the Pigsty installation directory
-i, --inventory PATHSelect the inventory
-o, --output FORMATOutput format: text (default), json, yaml, or json-pretty
--debugEnable debug logging
--log-level LEVELLog level: debug, info (default), warn, error, fatal, or panic
--log-path PATHWrite logs to a file; the default is the terminal

PIG-owned results support structured output. Raw-content commands such as inventory show and passthrough commands such as pt list retain their native output. See the command reference for details.

Structured results keep diagnostics and wrapped-tool chatter on stderr. JSON/YAML output and PIG_NON_INTERACTIVE=1 disable prompt input in PIG-owned command adapters and use sudo -n; they do not supply destructive-operation confirmation. Pass --yes where required. Documented data input, such as pig pg psql -f -, remains available. Native Patronictl forwarding retains its own interaction and output contract and rejects PIG structured-output modes.

Trust and configuration ownership

repo add writes the selected module files and preserves other files. repo set and repo add --remove back up and replace the existing definitions. If Ansible or another tool manages these files, keep the definitions in that tool’s configuration so its next run preserves your changes.

Pigsty signing key

When a module includes pigsty-infra or pigsty-pgsql, PIG reuses the existing public-key file or installs its embedded key with mode 0644:

PlatformPublic-key path
EL/etc/pki/rpm-gpg/RPM-GPG-KEY-pigsty
Debian / Ubuntu/etc/apt/keyrings/pigsty.asc

This step works offline. Selecting only other repositories, such as pgdg or node, does not prepare the Pigsty key.

Built-in repository definitions do not enforce package signatures by default: EL uses gpgcheck=0; Debian/Ubuntu uses trusted=yes. Ordinary repo add/set preserves these settings. pig sty boot enables Pigsty signature checks when key preparation succeeds. To require signatures, configure a trusted key and enable verification in the repository metadata.

If implicit key installation fails, the command warns and continues. The selected Pigsty definitions use trusted=yes, or gpgcheck=0 with repo_gpgcheck=0, and retain their default key reference. Structured results include the warning in data.warnings. APT may retain old indexes in this case; check the cache-update output.

An explicit key reference makes preparation mandatory:

  • On Debian/Ubuntu, signed-by names existing regular keyring files by absolute path. Separate multiple paths with commas.
  • On EL, gpgkey contains paths or literal URLs, which PIG passes to rpm --import.
  • PIG can install an explicitly referenced default Pigsty key from its embedded copy.

If preparation of an explicit key fails, repository configuration stops. Implicit installation prepares only the file and repository reference; explicit EL gpgkey also imports the key into RPM. See the design record for the rationale.

EL repositories retain DNF module filtering. Definitions with module_hotfixes=1, including Pigsty and PGDG, bypass module streams. PIG omits this key in EL7 configuration.

The current implementation prefers sow when it is available in PATH. On Linux, the SOW backend runs the equivalent of the following with sudo for every target directory:

sow create --pigsty --timeout 10m -- /absolute/repository/path

On macOS, install SOW first. It runs without sudo, and the default target is the current directory.

On Linux, if SOW is absent, PIG uses createrepo_c on EL or dpkg-scanpackages from dpkg-dev on Debian/Ubuntu. If SOW runs and fails, PIG returns the error. The 10m timeout limits the wait for SOW’s directory lock.

SOW’s --pigsty mode:

  1. Scans only top-level regular .rpm and .deb files—no recursion and no symlink following.
  2. Removes DEB packages for i386, and RPM/DEB packages named patroni with upstream version 3.0.4.
  3. Generates RPM/DEB metadata and writes repo_complete last. The marker contains SHA-256 hashes for remaining top-level packages, sorted by basename.

Documentation packages such as annobin-docs are retained unless another cleanup rule applies; a filename containing docs is not a reason to delete a package.

SOW preserves non-package files and directories. It stops if a package cannot be parsed or package coordinates conflict. The legacy backend uses different cleanup rules and records MD5 hashes in repo_complete. PIG checks that this file exists; it does not check its hashes. Use the list to verify package integrity before distributing an offline bundle.

build proxy

A matching macOS LaunchAgent generated by the older source without a management comment can upgrade without --replace. Recognition compares the complete generated plist; a comment alone does not grant ownership. Foreign or edited service files require --replace --yes. After the one-time comment migration, identical execution leaves the service running without a restart. This compatibility statement covers the verified old source format, not every released binary.

Set up Xray clients and servers for build environments with restricted internet access. The x alias is retained. With no arguments, pig build proxy installs or verifies Xray only. See the Xray design record for the design rationale.

Client

One command installs Xray if needed, writes the client configuration, starts its service, and checks HTTPS through both HTTP and SOCKS. The first listener defaults to 127.0.0.1:12345, with HTTP and SOCKS sharing that port. An omitted --listen preserves the listener of an existing supported client. The protocol is VLESS over RAW/TCP, REALITY, and xtls-rprx-vision, with a Chrome fingerprint and multiplexing disabled.

pig build proxy client 'vless://UUID@proxy.example.com:443?encryption=none&security=reality&type=tcp&flow=xtls-rprx-vision&sni=www.sraoss.co.jp&fp=chrome&pbk=PUBLIC_KEY&sid=SHORT_ID&pqv=VERIFY_KEY'
pig build proxy client --server proxy.example.com:443 --id UUID --sni www.sraoss.co.jp --public-key PUBLIC_KEY --short-id SHORT_ID --pqv VERIFY_KEY
pig build proxy client --from ./client.uri
pig build proxy client --from ./client.uri --listen 127.0.0.1:8888
pig build proxy client --from ./client.uri --plan

Choose one connection input: a positional URI, direct connection flags, or --from FILE/-. client.uri is simply a text file containing one standard vless:// URI, with an optional trailing newline; its name is arbitrary. --from - reads stdin. Do not mix input forms. --pqv supplies ML-DSA-65 verification when enabled on the server. Unsupported transports, duplicate URI parameters, and ambiguous inputs are rejected before setup.

On Linux, run setup as root or with sudo, with systemd running and a repository providing the Pigsty xray package configured first, for example sudo pig repo add infra -u. Setup uses /etc/xray.json with mode 0640 and ownership root:xray, the xray service account, and a PIG-owned systemd drop-in. On macOS, run as your regular user with Homebrew available. Setup uses ~/.config/xray/pig-proxy.json with mode 0600 and its own com.pigsty.xray-proxy LaunchAgent.

For an existing server, pass its connection URI directly to client setup:

# Linux client: the remote command only reads and exports the existing server connection.
ssh root@proxy.example.com 'pig build proxy server --host proxy.example.com --export-only --export -' | sudo pig build proxy client --from -
# macOS client: omit sudo.
ssh root@proxy.example.com 'pig build proxy server --host proxy.example.com --export-only --export -' | pig build proxy client --from -

Repeated setup reuses matching configuration and service state. To replace a different client configuration, use --replace --yes. Use --plan to preview the operation.

After setup, PIG requests https://www.google.com/generate_204 through both HTTP and SOCKS and requires HTTP 204. If the checks fail, PIG restores the previous configuration and service state. Any installed package remains.

The generated shell file defines po, px, and pck. To enable proxy variables in the calling shell:

# Linux
source /etc/profile.d/proxy.sh
po
# macOS
source ~/.config/xray/proxy.sh
po

Server

Server setup supports Linux with the same package, root, and systemd requirements. Require the advertised public --host and REALITY camouflage --target host:port. The first direct listener defaults to 0.0.0.0:443; --port changes the advertised public port and first direct listener. --listen sets an independent bind endpoint. The target must support TLS 1.3 and HTTP/2.

# Direct public listener; explicitly export a protected client URI file.
sudo pig build proxy server --host proxy.example.com --target www.sraoss.co.jp:443 --export ./client.uri
# Backend behind an already configured trusted PROXY-protocol ingress: 127.0.0.1:9443.
sudo pig build proxy server --host proxy.example.com --target www.sraoss.co.jp:443 --proxy-protocol --export ./client.uri
# Read an existing supported server and print its connection without changing the deployment.
sudo pig build proxy server --host proxy.example.com --export-only --export -

First setup generates a UUID, X25519 key pair, short ID, and ML-DSA-65 seed and verification key. SNI defaults to the --target hostname. Repeated setup preserves these credentials. If you omit --listen, it also preserves the listener; specify --listen to change it. Matching configuration does not restart the service. Conflicting targets or unsupported existing configurations produce an error.

Connection export options:

OptionPurpose
--export FILEWrite a client URI with mode 0600; identical content can be exported again, but different content is not overwritten
--export -Print the complete client URI on stdout and diagnostics on stderr
--export-onlyRead and export existing configuration without changing files or services; requires --export
--planPreview setup

Export requires text output. The URI contains client credentials, so pass it through a file or stdin. It does not contain the server’s private key or seed. When exporting an existing server, --host and --port specify the public endpoint the client reaches, not the backend listener.

After setup, test connectivity from a real client. Open the required firewall or cloud security-group rules. --proxy-protocol requires an existing trusted frontend and a loopback listener. PIG does not stop another service that occupies the port or remove an existing V2Ray installation.

Bootstrap stages

  1. On Debian 12/13, check and attempt to repair the en_US.UTF-8 locale.
  2. Check that Ansible runs and that its Python environment provides yaml, jmespath, and either cryptography or OpenSSL.
  3. Prepare the selected offline repository. If Ansible is unusable, install controller dependencies and check it again.
  4. Check helper tools, prepare key-based SSH to 127.0.0.1 for the invoking administrator, and attempt to initialize a missing ~/pigsty.

PIG prepares a selected or discovered offline repository even when Ansible already works. Use this command to stage offline packages on a ready controller.

Source selection and modes

The result records one of four bootstrap modes:

ModeMeaning
readyAnsible was already usable and no offline source needed preparation.
offlineAn explicit, discovered, or existing offline repository was selected.
onlineRegional online repositories were configured to repair the controller.
existingAn online refresh failed under --keep, and existing repository definitions were successfully used as a fallback.

PIG selects a source as follows:

  • --path accepts a local archive or an HTTP(S) URL. URL credentials are rejected, and a bad explicit source is a hard error rather than an online fallback.
  • An automatically discovered /tmp/pkg.tgz must be a regular, non-group/world-writable file owned by root or the invoking sudo user. Unsafe candidates are ignored with a warning.
  • A complete /www/pigsty repository takes precedence over a selected package. If both exist, the existing repository is reused and the package is left untouched with a warning.
  • Archives are downloaded and extracted by Pig itself. If /www does not exist, Pig creates /data/nginx and the expected /www -> /data/nginx symbolic link before committing content.

Offline mode enables only the strict pigsty-local repository. Online mode configures the selected region and installs the node and pigsty controller modules. It reuses or installs Pigsty’s embedded signing key and enables signature checks when key preparation succeeds. If implicit-key preparation fails, it records a warning and continues with the selected Pigsty repositories’ signature checks disabled. With explicit gpgkey or signed-by metadata, failure to prepare the referenced key is fatal; see pig repo.

Repository replacement and recovery

By default, PIG backs up existing definitions before writing new ones. If repository setup or package installation fails, it attempts to restore the backup and reports the result. --keep preserves existing definitions and allows a fallback to them if an online refresh fails.

Ansible installation or validation failure makes the command fail. Incomplete SSH, locale, or Pigsty-directory setup produces warnings.

  • -m|--mirror: equivalent to --region china; mutually exclusive with --region
  • -p|--path: offline package file or HTTP(S) URL; an invalid explicit source is a hard error
  • -k|--keep: preserve existing repositories instead of replacing them

Behavior Notes:

  • When the source instance is running, the command uses PostgreSQL low-level backup APIs to create a consistent physical copy; when the source is stopped, it can perform a cold copy.
  • The command prefers CoW/reflink. If only ordinary copy is available, interactive mode warns about disk-space risk and waits for confirmation.
  • The target cannot be /, /pg, source PGDATA, or a parent/child of source PGDATA. Symlinks are resolved before checking the source/destination relationship. /pg/data follows the same ownership, relationship, and runtime checks as other data directories.
  • Replacing a nonempty unmanaged target requires valid unmanaged pg_fork metadata in fork.json with an explicitly recorded target.data matching the directory. An arbitrary directory without PG_VERSION is not eligible for deletion. Missing, damaged, incomplete, or mismatched metadata is refused. An empty directory remains usable with --force. Managed forks must be replaced by name. A running or uncertain destination cannot be replaced. Forced removal by name still permits cleanup of a managed orphan under /pg/data-<name>.
  • Path validation resolves private directories as DBSU when the caller cannot traverse them; unresolved paths and source/destination aliases are refused.
  • Unmanaged fork removal checks an inaccessible target as the selected DBSU. The target must be a real directory; a symlink or failed check still prevents removal.
  • After copy, runtime and replication state is cleaned from the fork and fork.json is written. The new instance starts only when -s|--start is specified.
  • Managed forks must be managed by name. Unmanaged forks require --dst-data when starting, stopping, or removing.

List Forks:

Unknown state sets runtime_unknown: true in structured output without claiming that the fork has started. Lifecycle operations fail without rewriting metadata in that state.

JSON and YAML put fork records in the result’s data array. Records include source and target endpoints, copy and backup metadata, management commands, and PIG build metadata.

16 - pig pitr

Restore PostgreSQL to a selected recovery target with pgBackRest

Use pig pitr to restore a local PostgreSQL instance from pgBackRest backups. For a managed restore, PIG stops services as needed and restores the data. By default, it then starts PostgreSQL and leaves Patroni stopped for you to verify the recovered database.

Recovery replaces data in the target directory. Start with --plan to check the directory, backup source, recovery target, and service actions.

Before recovery

You need an installed pgBackRest, a readable configuration file, a usable backup, and the archived WAL needed to reach the target. The default config path is /etc/pgbackrest/pgbackrest.conf. Select another file with -c and a stanza with -s.

Run the commands on the host that contains the target data directory. PIG runs PostgreSQL and pgBackRest operations as --dbsu, then $PIG_DBSU, then postgres. Service operations require root privileges, directly or through sudo.

Use pig pb restore when you want to manage service shutdown and startup yourself.

Quick start

This example restores an existing managed data directory to a chosen time. Replace the timestamp with your recovery target:

# Inspect available backups
pig pb info

# Check the recovery plan
pig pitr -t "2025-01-15 09:30:00+08" --plan -- --delta

# Restore the data and start PostgreSQL
pig pitr -t "2025-01-15 09:30:00+08" -- --delta

# Connect to the recovered instance; use its actual data directory
pig pg psql -D /pg/data

--delta lets pgBackRest restore over an existing directory by comparing file checksums. PIG asks for y or yes before recovery. Use --yes for execution without a prompt.

For a time, name, LSN, transaction ID, or immediate target, PostgreSQL normally pauses when it reaches the target. Inspect the data before promotion. See post-recovery actions.

Managed directory and side restore

The managed directory comes from pg1-path in the selected stanza, then $PGDATA, then /pg/data. It must already contain an initialized PostgreSQL instance. An explicit -D that resolves to this same path is still a managed restore, including a symlink to it.

An explicit -D that resolves to a different path selects a side restore. PIG leaves Patroni and the managed instance alone. The side directory must exist, belong to the selected operating-system user, and be writable by that user. It can be empty.

The -D option selects only the data directory. If the backup contains tablespaces or external links, map them to separate paths. Add pgBackRest’s --tablespace-map and --link-map options after -- in the restore command.

A side restore requires --no-restart. The restored configuration retains the original port; start it manually with a free port:

# Prepare the directory as root or through sudo
sudo install -d -m 700 -o postgres -g postgres /tmp/pg-restore

# Restore backup files into the side directory
pig pitr -d -D /tmp/pg-restore --no-restart

# Start the side instance on a free port
pig pg start -D /tmp/pg-restore -O "-p 5433"
pig pg psql -D /tmp/pg-restore

pig pg psql -D reads the restored directory’s postmaster.pid to select its port and socket. It returns an error if it cannot resolve that instance.

Execution flow

  1. Validate options, configuration, target directory, stanza health, and available backups. If --set is given, check that the backup label exists.
  2. Show the operation and request confirmation, unless --yes is given.
  3. For a managed restore, stop an active Patroni service.
  4. Wait for PostgreSQL to stop, then retry fast shutdown if needed. Use --force-stop to allow immediate shutdown and a final process-termination attempt.
  5. Run pgbackrest restore.
  6. Start PostgreSQL unless --no-restart is given. For --default or --target-action=promote, wait until pg_is_in_recovery() is false. For other targets, verify recovery progress yourself.
  7. Print commands for data verification and the remaining recovery steps.

Declining confirmation or reaching EOF returns CodePITRConfirmationRequired (161001, exit status 7) before stopping Patroni or PostgreSQL, restoring data, or starting PostgreSQL.

An indeterminate PostgreSQL runtime state is an error, not proof that the instance is stopped. PIG will not restore over an unverified instance or use an unverified PID for forced termination. After restoration, an unknown runtime state cannot count as successful startup and prevents follow-up SQL checks against an unverified connection target.

--plan runs the prechecks and returns the planned actions. It needs access to the configuration, data directory, and backup repository, but does not stop services or restore data.

More examples

Run one recovery command for the target you need:

# Latest available state, restoring over an existing directory
pig pitr -d -- --delta

# Backup consistency point
pig pitr -I -- --delta

# Use a specific backup label
pig pitr -d -b 20251225-120000F -- --delta

# Restore files, then inspect them before starting PostgreSQL
pig pitr -d --no-restart -- --delta

# Promote automatically after a time target
pig pitr -t "2025-01-15 09:30:00+08" --target-action=promote -- --delta

Post-recovery actions

  1. Connect to the restored instance. Use its actual data directory:

    pig pg psql -D /pg/data

  2. Check recovery state, then verify the tables and records you need:

    SELECT pg_is_in_recovery() AS recovering,
       CASE WHEN pg_is_in_recovery() THEN pg_is_wal_replay_paused() END AS paused;

  3. If recovery is paused at the intended target and you want a writable primary, promote it:

    pig pg promote -D /pg/data

  4. For a Patroni-managed cluster, reconcile the restored instance with the cluster’s recovery plan, then resume Patroni with pig pt svc start. Handle other members and application routing as part of that plan.

If a managed restore fails after stopping Patroni, Patroni stays stopped. The target directory can contain a partial restore. Inspect PostgreSQL and pgBackRest logs, fix the failure, and complete recovery before starting Patroni. A startup timeout also needs investigation; it does not undo the restored files.

Structured output

Use --plan -o json to inspect a structured plan. Use --yes -o json to execute without interaction. YAML is also available.

Successful results include requested_data_dir, effective_data_dir, managed_data_dir, and side_restore in data. Follow-up commands are in the result’s top-level next_actions field.
