Planning Architecture and Nodes

How many nodes? Which modules need HA? How to plan based on available resources and requirements?

Pigsty uses a modular architecture. Select the modules for your requirements and define the deployment through declarative configuration.

Trade-offs

  • Monitoring requires at least 1 INFRA node. Production typically uses 2 nodes; large deployments use 3.
  • PostgreSQL HA requires at least 1 ETCD node. Production typically uses 3 nodes; large deployments use 5. An even-member ETCD cluster tolerates no more failures than an odd-member cluster with one fewer member. Prefer an odd number of members.
  • Silo object storage requires at least 1 MINIO node. Production typically uses 4 or more nodes in an MNMD cluster.
  • Production PostgreSQL clusters typically have at least two nodes: a primary and a replica. More demanding deployments use 3 nodes. Deployments with high read loads can have dozens of replicas.
  • Advanced PostgreSQL configurations include offline instances, synchronous instances, standby clusters, and delayed clusters.

Single-Node Setup

The single-node configuration puts all components on one node. It installs four core modules by default. Use it for demonstrations, development, or testing.

IDNODEPGSQLINFRAETCD
1node-1pg-meta-1infra-1etcd-1

An external S3/MinIO backup repository can supply the required recovery time and recovery point objectives (RTO/RPO). With this protection, a single-node configuration can serve standard production environments.

These single-node variants are available:

  • Rich (rich) is a production template with local Silo storage, a local software repository, and all PostgreSQL extensions.
  • Slim (slim) installs PGSQL and ETCD without the monitoring infrastructure. Slim Installation can expand to multiple nodes with HA.
  • Infra-only (infra) installs only INFRA to monitor other instances. It does not install database services.
  • Alternative kernels replace the standard PostgreSQL kernel with a derivative. Templates include pgsql, mssql, polar, ivory, and mysql. Other templates include pgtde, oriole, agens, and pgedge.

Two-Node Setup

The two-node configuration enables database replication and Semi-HA. It improves data redundancy and supplies limited automatic failover:

IDNODEPGSQLINFRAETCD
1node-1pg-meta-1 (replica)infra-1etcd-1
2node-2pg-meta-2 (primary)

Automatic recovery depends on which node fails:

  • If node-1 fails, manually promote node-2. Automatic failover is unavailable.
  • If node-2 fails, node-1 is automatically promoted.

Three-Node Setup

The three-node template deploys INFRA, ETCD, PGSQL, and MINIO (Silo) on every node. It tolerates one node failure when the remaining two can communicate and replica state permits failover. Silo uses a three-node, single-drive-per-node EC:1 pool. An existing single-node object store cannot be expanded directly into this topology; create a new pool and migrate objects.
