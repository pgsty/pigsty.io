Deployment

Multi-node, high-availability Pigsty deployment for production environments.

Production deployments require Architecture Planning and Preparation beyond the Getting Started procedure. This chapter describes the complete deployment process and recommended practices for production.

Before production deployment, test the workflow in the Pigsty Sandbox. Use Vagrant to create a local 4-node sandbox. Use OpenTofu to create a larger simulation environment in the cloud.

Production high availability typically requires at least three nodes. Review the core Concepts and common administration procedures before deployment. These procedures include Configuration, Ansible Playbooks, and Security Hardening for enterprise compliance.

1 - Install Pigsty for Production

How to install Pigsty on Linux hosts for production?

This guide describes production deployment on multiple nodes. For single-node demonstrations or development, use Getting Started.

Summary

  1. Prepare the nodes according to your architecture plan.
  2. Install a supported Linux operating system.
  3. Configure SSH access.
  4. Use an administration account with passwordless ssh and sudo access.
  5. Run the installation command:
curl -fsSL https://repo.pigsty.io/get | bash;         # International
curl -fsSL https://repo.pigsty.cc/get | bash;         # Backup Mirror

The installation script downloads and extracts Pigsty into your home directory. It also installs the dependencies. Then complete configuration and deployment.

Before you run deploy.yml, examine and edit pigsty.yml. This file is the configuration inventory.

cd ~/pigsty      # Enter Pigsty directory
./configure -g   # Generate config file (optional, skip if you know how to configure)
./deploy.yml     # Execute deployment playbook based on generated config

After deployment, open the Web UI through the IP address or domain on ports 80/443. Connect to PostgreSQL on port 5432.

Installation usually takes 3-10 minutes, depending on server resources and network speed. Offline installation can reduce this time. If you do not need monitoring, Slim Installation installs fewer components and takes less time.

Example: 20-node production simulation on Ubuntu 24.04, x86_64

demo/install-simu.cast — /demo/install-simu.cast

Install

Use one of these commands to install the Pigsty source package into ~/pigsty. This method is recommended and also installs Ansible and other deployment dependencies.

pigsty.io (Global)
curl -fsSL https://repo.pigsty.io/get | bash            # Install current default version
curl -fsSL https://repo.pigsty.io/get | bash -s v4.5.0  # Explicitly install the current public stable release
pigsty.cc (China)
curl -fsSL https://repo.pigsty.cc/get | bash            # Install current default version
curl -fsSL https://repo.pigsty.cc/get | bash -s v4.5.0  # Explicitly install the current public stable release

You can instead download a release or clone the source repository. If you use git, select a released version before deployment:

git clone https://github.com/pgsty/pigsty; cd pigsty;
git checkout v4.5.0;  # Always checkout a released tag when using git

After a manual download or clone, run bootstrap to install Ansible and the other dependencies. You can also install them yourself.

./bootstrap           # Install ansible for subsequent deployment

Configure

The inventory defines the deployment configuration. Pigsty uses pigsty.yml as the default configuration file. Edit it to define the required deployment.

The configure script is an optional configuration wizard. It generates an inventory with defaults for your environment:

./configure -g                # Use wizard to generate config with random passwords

The default output file is ~/pigsty/pigsty.yml. Examine this file and make the necessary changes before deployment.

Use the configuration templates as examples. You can also edit pigsty.yml directly without the wizard:

./configure -c ha/full -g       # Use 4-node sandbox template
./configure -c ha/trio -g       # Use 3-node minimal HA template
./configure -c ha/dual -g -v 18 # Use 2-node semi-HA template with PG 18
./configure -c ha/simu -s       # Use 20-node production simulation, skip IP check, no random passwords

Upstream changes can stop installation

Incorrect updates to Linux or PGDG repositories can break dependencies and cause deployment failures. These failures are common. For production, we strongly recommend verified offline packages for offline installation.

Repeated deployment can change services

Another run of deploy.yml on an existing deployment can restart services and overwrite configuration files. Examine the required changes before you run it again.

2 - Prepare Resources for Serious Deployment

Production deployment preparation including hardware, nodes, disks, network, VIP, domain, software, and filesystem requirements.

Pigsty runs on nodes, which can be physical machines or virtual machines. This document describes the planning and preparation for deployment.

Node

Pigsty runs on the Linux kernel with x86_64 or aarch64 architecture. A node supplies a bare Linux operating system that you can access through SSH. It can be a physical machine, virtual machine, or container with systemd support. The node must have systemd, sudo, and sshd.

A deployment requires at least 1 node. You can deploy to multiple nodes in one playbook run, or add nodes later. The minimum resources are 1C1G; we recommend at least 1C2G. There is no upper resource limit. Pigsty automatically tunes parameters for the available resources.

Select the node count for your requirements; see Architecture Planning. A single-node deployment with external backups provides recovery protection. For production, we recommend multiple nodes. A working HA deployment requires at least 3 nodes. A 2-node deployment provides Semi-HA.

Disk

Pigsty uses /data as the default data directory. If you have a dedicated data disk, mount it at /data. Use /data1, /data2, and /dataN for additional disks.

To change a data directory, set the applicable parameter:

NameDescriptionDefault
node_dataNode main data directory/data
pg_fs_mainPG main data directory/data/postgres
pg_fs_backupPG backup directory/data/backups
etcd_dataETCD data directory/data/etcd
infra_dataInfra data directory/data/infra
nginx_dataNginx data directory/data/nginx
minio_dataSilo data directory/data/minio
redis_fs_mainRedis data directory/data/redis
kafka_dataKafka data directory/data/kafka

The native MySQL 8.4 pilot module always uses /var/lib/mysql. It does not currently expose a data-directory parameter.

Filesystem

You can use any supported Linux filesystem for data disks. For production, we recommend xfs.

xfs is a standard Linux filesystem with good performance. Its copy-on-write (CoW) support permits instant cloning of large database clusters. Silo deployments with multiple drives require xfs.

ext4 is another supported choice. It has more data recovery tools but does not support CoW. zfs supplies RAID and snapshots, but adds significant performance overhead and requires separate installation.

Select the filesystem for your requirements. Avoid NFS for database services.

Pigsty expects root:root ownership and 755 permissions on /data. Administrators can assign ownership to directories directly under /data. Each application runs with a dedicated account in its own subdirectory. See FHS for the directory structure.

Network

The default online installation requires outbound Internet access. Offline installation does not require Internet access.

Assign a fixed IPv4 address to each node for internal communication. Pigsty uses this primary address on the main network interface as the unique node identifier. If a single-node deployment has no fixed IP address, use 127.0.0.1.

Use an internal node address

Public IP addresses as node identifiers can cause security and connection problems. Always use internal IP addresses for node identifiers.

VIP

Pigsty supports optional Layer 2 virtual IP addresses (L2 VIPs). NODE clusters use keepalived; PGSQL clusters use vip-manager.

To use this feature, assign an L2 VIP address to each node or database cluster. This is usually straightforward on your own hardware. Public cloud networks can make this configuration difficult.

L2 VIP requires an L2 network

For Node VIP or PG VIP, all participating nodes must use the same L2 network.

CA

Pigsty creates a self-signed certificate authority (CA) for each deployment. The CA issues the encryption certificates.

You can instead use an existing enterprise CA or self-signed CA to issue the required certificates.

Domain

Pigsty uses the local static domain i.pigsty for the Web UI by default. You can also use the node IP address.

For production, we recommend a domain name to enable HTTPS and encrypted data transfer. Domain names also let multiple services share one port.

For Internet access, use a public DNS provider, such as Cloudflare or AWS Route53. Point the domain to the node’s public IP address. For LAN or office access, use internal DNS with the node’s internal IP address.

For local access, add this entry to /etc/hosts on each computer that accesses the Web UI:

10.10.10.10 i.pigsty    # Replace with your domain and Pigsty node IP

Linux

Pigsty runs on Linux and currently targets 16 platform combinations. These combinations cover eight distribution major versions and two architectures. See the Compatible OS List.

The recommended operating system versions are:

  • Rocky Linux 9.8 / 10.2.
  • Debian 12.15 / 13.6.
  • Ubuntu 22.04.5 / 24.04.4 / 26.04.0.

On macOS or Windows, use a virtual machine or a Docker image with systemd.

We strongly recommend a fresh operating system installation. If the server already runs Nginx, PostgreSQL, or similar services, consider a new node.

Use the same operating system on all nodes

In a multi-node deployment, use the same Linux distribution, architecture, and version on every node. Mixed environments can work, but they are unsupported and can cause unpredictable problems.

Locale

We recommend en_US as the primary operating system language so PostgreSQL writes logs in English. At minimum, make sure that this locale is available.

Some distributions, including Debian, do not always supply en_US by default. Use these commands to enable it:

localedef -i en_US -f UTF-8 en_US.UTF-8
localectl set-locale LANG=en_US.UTF-8

For PostgreSQL 17 and later, we strongly recommend the built-in C.UTF-8 collation as the default. The configuration wizard selects C.UTF-8 when the PostgreSQL version and operating system support it.

Ansible

Pigsty uses Ansible on the administration node to control all managed nodes. See Installing Ansible.

By default, Pigsty installs Ansible on INFRA nodes. These nodes can serve as administration nodes or backup administration nodes. In a single-node deployment, one node has both roles. It is the administration node that runs Ansible and the INFRA node that hosts infrastructure.

Pigsty

Use one of these commands to install the current default Pigsty source:

curl -fsSL https://repo.pigsty.io/get | bash;
pigsty.cc (China)
curl -fsSL https://repo.pigsty.cc/get | bash;

3 - Planning Architecture and Nodes

How many nodes? Which modules need HA? How to plan based on available resources and requirements?

Pigsty uses a modular architecture. Select the modules for your requirements and define the deployment through declarative configuration.

Common Patterns

Select the architecture for your reliability requirements and available resources. Production deployments with full high availability require at least 3 nodes. With 2 nodes, use the Semi-HA configuration.

Architecture planning service

Architecture Consulting Services can help you plan the Pigsty configuration.

Trade-offs

  • Monitoring requires at least 1 INFRA node. Production typically uses 2 nodes; large deployments use 3.
  • PostgreSQL HA requires at least 1 ETCD node. Production typically uses 3 nodes; large deployments use 5. An even-member ETCD cluster tolerates no more failures than an odd-member cluster with one fewer member. Prefer an odd number of members.
  • Silo object storage requires at least 1 MINIO node. Production typically uses 4 or more nodes in an MNMD cluster.
  • Production PostgreSQL clusters typically have at least two nodes: a primary and a replica. More demanding deployments use 3 nodes. Deployments with high read loads can have dozens of replicas.
  • Advanced PostgreSQL configurations include offline instances, synchronous instances, standby clusters, and delayed clusters.

Single-Node Setup

The single-node configuration puts all components on one node. It installs four core modules by default. Use it for demonstrations, development, or testing.

IDNODEPGSQLINFRAETCD
1node-1pg-meta-1infra-1etcd-1

An external S3/MinIO backup repository can supply the required recovery time and recovery point objectives (RTO/RPO). With this protection, a single-node configuration can serve standard production environments.

These single-node variants are available:

  • Rich (rich) is a production template with local Silo storage, a local software repository, and all PostgreSQL extensions.
  • Slim (slim) installs PGSQL and ETCD without the monitoring infrastructure. Slim Installation can expand to multiple nodes with HA.
  • Infra-only (infra) installs only INFRA to monitor other instances. It does not install database services.
  • Alternative kernels replace the standard PostgreSQL kernel with a derivative. Templates include pgsql, mssql, polar, ivory, and mysql. Other templates include pgtde, oriole, agens, and pgedge.

The two-node configuration enables database replication and Semi-HA. It improves data redundancy and supplies limited automatic failover:

IDNODEPGSQLINFRAETCD

  • If node-1 fails, manually promote node-2. Automatic failover is unavailable.
  • If node-2 fails, node-1 is automatically promoted.

4 - Setup Admin User and Privileges

Admin user, sudo, SSH, accessibility verification, and firewall configuration

Pigsty uses an operating system administration account with SSH and sudo access to every managed node. The account must be able to log in through SSH and run sudo commands on these nodes. Passwordless access is the standard configuration; password prompts are also supported.

User

Use an account name such as dba or admin. Avoid root and postgres:

  • You can deploy as root, but this is not recommended for production.
  • Do not use postgres (pg_dbsu) as the administration account.

Passwordless

You can enter passwords for each ssh and sudo command instead of configuring passwordless access. When you run playbooks, use -k|--ask-pass for the SSH password prompt. Use -K|--ask-become-pass for the sudo password prompt:

./deploy.yml -k -K

If your security policy prohibits passwordless ssh or sudo, use these options. You can also configure a longer sudo password cache time in sudoers to reduce repeated prompts.

Create Admin User

Your server or virtual machine provider usually creates an initial administration account. If you need a different account, the deployment playbook can create one.

Use an existing administration account or root access to create the new account:

./node.yml -k -K -t node_admin \
  -e ansible_user=[current_login_admin] \
  -e node_admin_username=[new_admin_to_create]

The existing account creates a dedicated dba account with UID 88 by default. The playbook also configures sudo and SSH access. These parameters control the account:

NameDescriptionDefault
node_admin_enabledEnable node admin usertrue
node_admin_uidNode admin user UID88
node_admin_usernameNode admin usernamedba

Sudo

Give the administration account sudo access on every managed node. Passwordless sudo is recommended.

For an account named vagrant, create or edit its sudoers file:

echo '%vagrant ALL=(ALL) NOPASSWD: ALL' | sudo tee /etc/sudoers.d/vagrant

For the dba account, use this content in /etc/sudoers.d/dba:

%dba ALL=(ALL) NOPASSWD: ALL

If your security policy prohibits passwordless sudo, remove NOPASSWD::

%dba ALL=(ALL) ALL

Ansible uses sudo to run commands with root privileges on managed nodes. If an environment has no sudo, install it first. This can apply to Docker containers.

SSH

The current local account should have passwordless SSH access to the administration account on every managed node. The local and remote account names can differ. The following procedures describe the basic SSH configuration.

Generate SSH Key

If you do not have an SSH key pair, generate one:

ssh-keygen -t rsa -b 2048 -N '' -f ~/.ssh/id_rsa -q

The bootstrap script also generates a key pair if none exists.

Copy SSH Key

Copy the public key to the administration account’s ~/.ssh/authorized_keys file on every node, including the local node. Use ssh-copy-id:

ssh-copy-id <ip>                        # Interactive password entry
sshpass -p <password> ssh-copy-id <ip>  # Non-interactive (use with caution)

Using Alias

If a node requires a jumpserver, another port, or different credentials, define an SSH alias in ~/.ssh/config:

Host meta
    HostName 10.10.10.10
    User dba                      # Different user on remote
    IdentityFile /etc/dba/id_rsa  # Non-standard key
    Port 24                       # Non-standard port

Set ansible_host to this SSH alias in the inventory:

nodes:
  hosts:          # If node `10.10.10.10` requires SSH alias `meta`
    10.10.10.10: { ansible_host: meta }  # Access via `ssh meta`

Ansible can also use SSH connection parameters directly. See the Ansible Inventory Guide.

This method supports private nodes behind jumpservers and nodes with different ports or credentials. It also lets you use a local laptop as the administration node.

Check Accessibility

From the administration node, the current account should reach every managed node through passwordless ssh. The remote administration account should also have passwordless sudo access.

Run this command from the administration node for each managed node:

ssh <ip|alias> 'sudo ls'

If the command returns without a password prompt or error, passwordless SSH and sudo access work.

Firewall

For production, configure the firewall to block unauthorized access to service ports. By default, block inbound access from office and Internet networks except these ports:

  • 22 for SSH node access.
  • 80 for HTTP and 443 for HTTPS Web UI access.
  • 5432 for PostgreSQL access.

If clients use other PostgreSQL service ports, permit those ports as required. See the complete port list.

  • 5432: PostgreSQL database.
  • 6432: PgBouncer connection pooler.
  • 5433: PostgreSQL primary service.
  • 5434: PostgreSQL replica service.
  • 5436: PostgreSQL default service.
  • 5438: PostgreSQL offline service.

7 - OpenTofu

Create virtual machine environments on public clouds with OpenTofu

OpenTofu is an open-source infrastructure-as-code tool. It creates public cloud virtual machines from configuration files.

Pigsty uses OpenTofu by default. It supplies Terraform-compatible .tf templates for Alibaba Cloud, global AWS, AWS China, Azure, GCP, Tencent Cloud, Hetzner, Vultr, DigitalOcean, and Linode. The aliyun-s3.tf template also creates a private OSS bucket and dedicated RAM read/write credentials for S3 and pgBackRest.

Quick Start

Install OpenTofu

On macOS, install OpenTofu with Homebrew:

brew install opentofu
tofu version

For Debian, Ubuntu, RHEL, or another platform, use the OpenTofu installation guide. The package and command name is tofu.

Initialize and Apply

Enter the cloud template directory. Select a template, initialize the provider plugins, and examine the deployment plan:

cd ~/pigsty/terraform
cp spec/aliyun.tf terraform.tf         # Select template
tofu init                              # Install cloud provider plugins (first use)
tofu plan                              # Review the execution plan
tofu apply                             # Create resources after interactive confirmation

After you review the plan, run tofu apply. Enter yes to confirm. OpenTofu then creates the virtual machines and related cloud resources.

Get IP Address

After creation, print the administration node’s public IP address:

tofu output -raw meta_ip

Configure SSH Access

Global cloud templates usually supply an executable ssh_command output:

tofu output -raw ssh_command

The repository’s ./ssh script supports legacy templates whose outputs contain only IP addresses. These templates use the root password PigstyDemo4. The script treats each infrastructure-as-code output as an IP address and writes it to ~/.ssh/pigsty_config. It then distributes keys with sshpass.

Compatible templates include aliyun.tf, aliyun-full.tf, aliyun-oss.tf, and aliyun-pro.tf. Do not use this script with modern templates that output ssh_command, private IP addresses, or access keys.

For a compatible template, run:

./ssh       # Write SSH config and distribute keys
ssh meta    # Login using hostname instead of IP
Load the SSH configuration

To use ~/.ssh/pigsty_config, include it from ~/.ssh/config:

Include ~/.ssh/pigsty_config

Destroy Resources

After testing, use this command to remove the cloud resources:

tofu destroy

Terraform Compatibility and Migration

OpenTofu supports the existing names terraform/, .tf, terraform.tfvars, .terraform.lock.hcl, and terraform.tfstate for compatibility. The repository keeps these names. You can explicitly select Terraform as a compatibility option:

make IAC_CLI=terraform plan

Use only one infrastructure command-line tool in a working directory at a time. Before you migrate existing state, preserve it and compare both plans:

cp -p terraform.tfstate "terraform.tfstate.pre-tofu.$(date +%Y%m%d%H%M%S)"

tofu init
tofu plan

Continue only if the OpenTofu plan contains the expected changes. Do not delete terraform.tfstate when you initialize providers again.

8 - Security Considerations

Credential, network, authentication, encryption, data protection, and audit checks for production Pigsty deployments.

Pigsty defaults support development, testing, and demonstrations on a trusted intranet. For production, configure credentials, network boundaries, authentication, certificates, backups, and audit controls for your threat model.

Security and Compliance describes the mechanisms and their limits. Use the Launch Hardening Checklist for executable checks. The ha/safe template is a hardening example. Review each control for your environment before you use it.

Confidentiality

Critical Files

Protect these assets:

  • pigsty.yml and other inventories. They normally contain system and application credentials.
  • files/pki/ca/ca.key. This key can issue certificates that the deployment trusts.
  • The administration account’s SSH private key. By default, this account can use sudo on managed nodes.
  • Private keys for client certificates and backup encryption.
  • Generated /pg/tmp/pg-user-*.sql files.

Restrict access to the administration node and configuration repository. Do not commit complete inventories or private keys to public repositories. Use controlled channels to back up the CA private key and recovery configuration.

Passwords

Replace every public default credential before production deployment. Start with this command:

./configure -g

This option does not replace the pgBackRest cipher_pass or user-defined credentials. It also leaves some Silo example credentials in ha/safe unchanged. Examine the result against the Default Credentials Checklist.

PostgreSQL uses SCRAM-SHA-256 for new or updated passwords by default. To enforce password complexity, preload passwordcheck through pg_libs, or configure credcheck. Set the account lifetime with expire_in or expire_at.

Before credential rotation, prepare a rollback plan. Update the database users, PgBouncer user list, component configuration, and client connection information during rotation.

Network Boundaries

IP Addresses

PostgreSQL listens on 0.0.0.0 by default. To restrict its listen addresses, set these parameters:

pg_listen: '${ip},${vip},${lo}'

The listen address supplies only part of the network boundary. Also review these controls:

  • Cloud security groups or upstream firewalls.
  • node_firewall_public_port.
  • The trusted CIDRs in node_firewall_intranet. Make sure that these ranges are not too broad.
  • PostgreSQL and PgBouncer HBA rules.
  • The Patroni REST API allowlist.

The demonstration pigsty.yml also exposes 5432 to public networks. Remove that exception for production. If applications require direct database access, permit only their specific CIDRs.

Network Traffic

  • PostgreSQL enables server-side TLS by default. The default intranet HBA rules do not require TLS.
  • PgBouncer TLS is disabled by default. pgbouncer_sslmode controls this setting.
  • HTTPS for the Patroni REST API is disabled by default. patroni_ssl_enabled controls this setting.
  • Nginx and the object-storage backend selected by MINIO enable HTTPS by default. Etcd uses TLS for client and peer traffic.

HBA auth: ssl requires encryption but does not verify the server identity for the client. Clients should use sslmode=verify-full with a trusted CA to verify the database server. See Encrypted Communication.

Grafana, VictoriaMetrics, and other components can listen on node ports. The default firewall does not expose these ports directly to public networks. Prefer Nginx for external access. Restrict management pages by source address and identity.

Authentication and Access Control

  • Use HBA to define the user, database, source address, and authentication method. Avoid broad world rules.
  • Use auth: cert for privileged remote users. Establish a process to deliver and revoke client certificates.
  • Assign application privileges through built-in roles. Do not grant superuser privileges to ordinary application accounts.
  • Set revokeconn: true for shared multi-tenant clusters. Examine the effective database ACLs.
  • Create objects through the declared database owner or a controlled administration role so default privileges apply.
  • To isolate offline queries, explicitly set role: offline on the HBA rule for dbrole_offline.

After changes to HBA, users, or roles, compare the inventory with the effective database state.

Integrity

Pigsty enables page checksums by default to detect damage after page writes. These checksums do not detect every memory error, logical error, or incorrect application write.

The CRIT template enables Patroni strict synchronous mode and more detailed connection logs. This mode aims to preserve acknowledged transactions. The result depends on synchronous_commit, the state of synchronous replicas, and the failover conditions. Writes block when no synchronous replica is available.

CRIT sets the watchdog mode to automatic. The watchdog activates only if the system has a usable watchdog device. Decide whether required is appropriate for your hardware and availability requirements.

Availability

  • Critical clusters should normally have at least three instances in independent failure domains.
  • Connect through HAProxy, a VIP, or a DNS service name instead of a fixed primary address.
  • Use an odd number of etcd nodes in independent failure domains.
  • Remove single points of failure in INFRA, DNS, monitoring, and software repositories where your availability requirements demand it.
  • Understand the configuration semantics of pg_rpo and pg_rto. Test the recovery objectives through exercises.

Replicas handle some node failures. They do not replace backups.

Backup and Recovery

  • The local pgBackRest repository has no encryption by default. It shares a failure domain with the database host.
  • The pgbackrest_method: minio repository uses AES-256-CBC by default. Replace the public default cipher_pass: pgBackRest.
  • The pgBR.${pg_cluster} value in ha/safe is also an example. Do not use it as the final encryption key.
  • Store important backups in an independent failure domain. Evaluate object locking, versioning, or offline copies for additional protection.
  • Test full restores and PITR regularly. Verify the WAL, keys, recovery time, and application consistency.

See Data Security and Backup and Recovery.

Audit and Response

The default OLTP template logs DDL, slow queries, and PostgreSQL 18 connection-authorization events. CRIT also logs connection and disconnection events.

Install and preload pgaudit, then configure an audit policy. The package alone does not produce SQL audit logs. If you enable Vector and VictoriaLogs, set log retention, access, and archive policies for your requirements.

Metrics, logs, and alerts supply information for incident response. Production also requires alert classification, on-call ownership, incident determination, response, evidence collection, and a review after each incident.

Host and Software Supply Chain

  • After compatibility validation, change SELinux from the default permissive mode to enforcing.
  • Disable unnecessary SSH password authentication and remote root login. Consider a bastion host or multi-factor authentication.
  • Review the sudo permissions of the administration and database operating system accounts.
  • Keep Pigsty and upstream components on current, supported versions.
  • Verify the software repository GPG key fingerprint. Enable signature verification for each package where required.
