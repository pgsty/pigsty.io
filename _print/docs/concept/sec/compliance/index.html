Compliance

Compliance combines configuration, process, and evidence. This page covers launch hardening, MLPS and SOC 2 control mappings, supply-chain integrity, and vulnerability response.

Compliance requires continuous evidence of three elements:

  • Configuration: Security controls must be enabled. Pigsty directly provides configuration.
  • Process: The organization must establish access approval, change management, recovery exercises, and related procedures.
  • Evidence: Records must show that configuration and processes remain effective. The inventory, runtime logs, and monitoring system provide part of this evidence.

This page provides a pre-launch checklist and maps Pigsty capabilities to common compliance frameworks. These mappings support architecture and gap analysis. They are not an MLPS assessment, SOC 2 audit opinion, or legal advice.

Launch Hardening Checklist

Before deployment:

  • Define the network boundary. Do not expose database ports publicly. Remove the demo firewall exception for 5432.
  • Select the built-in CA or enterprise PKI. See Using an Enterprise CA.
  • Plan client verification. Set sslmode=verify-full and a trusted CA on database clients.
  • Assign application accounts through the four-tier roles. Declare expire_in.
  • Plan the backup repository, retention, encryption passphrase, and off-site copies.
  • Decide whether to use ha/safe and the CRIT parameter template.

After deployment:

  • Confirm that all default credentials have changed. Include values covered by configure -g and uncovered backup, object storage, and custom credentials.
  • Compare /pg/data/pg_hba.conf with the declared HBA policy and intended access boundary.
  • Query effective users, roles, default privileges, and database CONNECT grants. Compare them with the inventory.
  • Run a full backup and recovery exercise to validate the backup path.
  • Confirm log collection, monitoring alerts, and notification channels.

Periodically:

  • Audit privileges: compare pg_users declarations with effective grants, and remove expired or departed-user accounts
  • Rotate credentials and certificates
  • Exercise recovery and failover
  • Track security updates for Pigsty and upstream components

Supply Chain and Vulnerability Response

Compliance reviews also cover the software supply chain. Pigsty provides these distribution and response controls:

Package integrity: Pigsty repository RPM and DEB packages (repo.pigsty.io, repo.pigsty.cc) are GPG-signed. Verify fingerprint 9592 A7BC 7A68 2E73 3337 6E09 E793 5D8D B9BD 8B20 (B9BD8B20) before trusting the key. Deployment-generated repository definitions and the INFRA node local repository do not enforce verification for every package by default. In production, review package-manager trust and signature settings.

Vulnerability response: Report issues privately through GitHub vulnerability reporting or email as specified in SECURITY.md. The project targets acknowledgment within three business days and initial assessment within seven days.

Version support: Security fixes ship in the latest stable release. Update to receive them. Subscription services provide extended support for users who must retain a version longer.
