pig postgres

Manage local PostgreSQL server with pig postgres subcommand

pig postgres (alias pig pg) manages local PostgreSQL instances and databases. Use it to initialize or control an instance, run SQL, maintain tables, and create database copies. Use pig pt for Patroni cluster operations and pig pitr for recovery with pgBackRest.

Commands run as the PostgreSQL operating-system user, normally postgres. Install PostgreSQL first. For a new data directory, make its parent writable by that user or create an empty directory with the correct ownership before running pg init.

Connect to an instance

For a running instance at /pg/data, check its status and connect:

pig pg status -D /pg/data
pig pg psql -D /pg/data

Use the instance’s actual data directory. In psql, run SQL commands, then type \q to exit. To install PostgreSQL and create a test instance, follow Getting Started.

Global Options

These options apply to all pig pg subcommands:

OptionShortDefaultDescription
--version-vauto-detectPostgreSQL major version
--data-D/pg/data for instance operationsData directory path
--dbsu-UpostgresPostgreSQL operating-system user; $PIG_DBSU overrides the default

Use pig pg svc ... to control the postgres systemd unit. Use the instance commands (start, stop, and so on) to operate on -D with pg_ctl, defaulting to /pg/data. An explicit empty or whitespace-only -D / --data is a parameter error; it does not select a default target.

When -D is explicitly supplied, psql, ps, kill, vacuum, analyze, freeze, and repack connect to that directory’s instance, including database enumeration for --all. Before using its recorded port and socket, PIG verifies that the PID is live and identifies a PostgreSQL process. Missing, stale, invalid, or mismatched metadata and unknown process identity fail before a SQL client runs, without falling back to another connection target. Without -D, these SQL commands retain native client connection defaults and any PGHOST/PGPORT visible to the client; PIG does not add host or port arguments or bind the connection to /pg/data. To explicitly target a TCP-only instance, use the native client with connection options. pg clone and pg fork retain their separate port options.

Plans, confirmation retries, and verification commands for promote, vacuum, and repack preserve the selected data directory, PostgreSQL version, and operating-system user. This includes an explicit -D /pg/data; omitting -D continues to preserve native SQL connection defaults. VACUUM FULL plans report confirmation as required, matching execution. Generated maintenance commands put the database name after --, so a name such as --all cannot become an option when the command is copied and executed.

PIG_NON_INTERACTIVE=1 and JSON/YAML output disable prompt stdin and use non-interactive sudo. Native passthrough retains its interaction contract; explicit data input such as psql -f - remains available.

Version Detection Logic:

  1. If -v specified, use that version
  2. Otherwise read from PG_VERSION file in data directory
  3. Otherwise use the default PostgreSQL installation found by PIG.

Service Control Commands

pg init

Initialize PostgreSQL data directory. Wraps initdb.

  • Use an empty directory, or a path that the database operating-system user can create.
  • Data checksums are enabled. Use -K to disable them.
  • Encoding is UTF8. PostgreSQL 17+ uses the built-in C.UTF-8 locale. Earlier versions use the system C.UTF-8 locale when available, otherwise C.
  • An initialized directory requires --force, which removes its existing data after confirmation. A running instance cannot be overwritten. If its running state cannot be verified, initialization fails before removal and reports the probe error instead of claiming that PostgreSQL is running.
  • Put extra initdb arguments after --. To choose another locale or encoding, run initdb directly.
pig pg init                       # Initialize with defaults
pig pg init -v 18                 # Specify PostgreSQL 18
pig pg init -D /data/pg18         # Specify data directory
pig pg init -K                    # Disable data checksums
pig pg init -f                    # Force init (remove existing data)
pig pg init -- --waldir=/wal      # Pass extra args to initdb

Options:

OptionShortDefaultDescription
--no-data-checksums-KfalseDisable data checksums
--force-ffalseRemove an initialized directory and initialize it again
--yes-yfalseSkip overwrite confirmation when used with --force

pg start

Start PostgreSQL with pg_ctl start. For a Patroni-managed instance, prefer pig pt start so PostgreSQL starts under Patroni. For a systemd-managed PostgreSQL service, use pig pg svc start.

pig pg start                      # Start with defaults
pig pg start -D /data/pg18        # Specify data directory
pig pg start -l /pg/log/pg.log    # Redirect output to log file
pig pg start -O "-p 5433"         # Pass options to postgres
pig pg start -o json              # Structured JSON output

Options:

OptionShortDescription
--log-lStartup log; default /tmp/pig-pg-start.log
--timeout-tWait timeout: $PGCTLTIMEOUT, then 60 seconds
--no-waitDon’t wait for startup completion
--options-OOptions to pass to postgres

If PostgreSQL is already running, the command prints the existing postmaster PID and returns successfully.

pg stop

Stop PostgreSQL with pg_ctl stop.

On a Patroni-managed instance, stopping PostgreSQL directly can make Patroni restart it or initiate failover. Use pig pt svc stop to stop the manager first, then check the PostgreSQL state.

pig pg stop                       # Fast shutdown (default)
pig pg stop -m smart              # Wait for clients to disconnect
pig pg stop -m immediate          # Immediate shutdown
pig pg stop --plan                # Preview stop plan

Options:

OptionShortDefaultDescription
--mode-mfastShutdown mode: smart/fast/immediate
--timeout-t60Wait timeout in seconds; $PGCTLTIMEOUT overrides the default
--no-waitfalseDon’t wait for shutdown completion
--planfalsePreview local pg_ctl stop plan only

Shutdown Modes:

ModeDescription
smartWait for all clients to disconnect
fastRollback active transactions, disconnect clients, clean shutdown
immediateTerminate all processes immediately, requires recovery on next start

pg restart

Restart PostgreSQL server.

pig pg restart                    # Fast restart
pig pg restart -m immediate       # Immediate restart
pig pg restart -O "-p 5433"       # Restart with new options
pig pg restart --plan             # Preview restart plan

Options: Same as pg stop, plus --options (-O) to pass to postgres.

pg reload

Reload PostgreSQL configuration. Sends SIGHUP signal to server.

pig pg reload                     # Reload configuration
pig pg reload -D /data/pg18       # Specify data directory

pg status

Show the selected instance’s state:

pig pg status
pig pg status -D /data/pg18
pig pg status -D /data/pg18 -o json

Text output includes pg_ctl status, a compact pg_controldata summary, processes owned by the database operating-system user, and related services. The postgres row reflects the selected instance’s process state. Service rows cover patroni, pgbouncer, vip-manager, and haproxy.

Structured output describes the selected instance, including its data directory, version, PID, port, and available control-file information.

A missing process or a PID independently identified as a different executable is stale. EPERM alone never proves that PostgreSQL has stopped. If process identity cannot be established, the state remains unknown and cannot authorize forced initialization or PITR restore. Plans report an indeterminate running-state check as unknown, without a usable PID or a passed precondition. pg status returns 130201 (exit 3) for permission failures and 130808 (exit 1) for other status-probe failures, such as invalid PID metadata or unavailable process identity. These results have success: false; their partial data does not establish that PostgreSQL is stopped. Stale PIDs no longer make PIG report an unrelated process as PostgreSQL; pg_ctl and PostgreSQL retain their own lock-file checks and may still require operator cleanup after a crash. A PID file copied from another directory does not identify the selected instance.

pg promote

Timeline reporting uses the selected instance’s port and socket. If its PID metadata cannot be resolved, PIG reads that directory’s control data or leaves the timeline unknown. This does not change promotion execution or its primary-role success check.

Promote a standby or a paused recovery instance to a writable primary. Use --plan to inspect the action. Text mode requests confirmation; structured execution requires --yes.

pig pg promote                    # Promote replica
pig pg promote -D /data/pg18      # Specify data directory
pig pg promote --plan             # Preview promotion plan
pig pg promote -y                 # Skip confirmation prompt

Options:

OptionShortDescription
--timeout-tWait timeout: $PGCTLTIMEOUT, then 60 seconds
--no-waitDon’t wait for promotion completion
--planPreview promotion plan only
--yes-ySkip confirmation prompt

pg role

Detect PostgreSQL instance role (primary or replica).

pig pg role                       # Output: primary, replica, or unknown
pig pg role -V                    # Verbose output, show detection process
pig pg role -D /data/pg18         # Specify data directory

Options:

OptionShortDescription
--verbose-VShow detailed detection process

Output:

  • primary: Current instance is primary
  • replica: Current instance is replica
  • unknown: Cannot determine instance role

Detection Strategy (by priority):

  1. Target process detection: Read the selected postmaster.pid, then inspect only that postmaster’s process tree
  2. Bound SQL query: Use the selected instance’s port/socket and verify data_directory before trusting pg_is_in_recovery()
  3. Data directory check: Check for standby.signal, recovery.signal, recovery.conf files

File-based role detection does not establish whether PostgreSQL is running. A stopped instance can still report its configured role, but a stale PID file never makes it appear alive. If the running-state probe fails, the command returns an error instead of reporting a role as verified.

Connection & Query Commands

pg psql

Connect to PostgreSQL database via psql.

pig pg psql                       # Connect to postgres database
pig pg psql mydb                  # Connect to specific database
pig pg psql mydb -c "SELECT 1"    # Execute single command
pig pg psql -f script.sql         # Execute SQL script file

Options:

OptionShortDescription
--command-cExecute single SQL command
--file-fExecute SQL script file

With -D, PIG reads that directory’s postmaster.pid as the selected operating-system user. It verifies the live process before connecting to the recorded port and Unix socket. A stopped or uncertain target returns an error. Without -D, psql retains its native connection defaults and any PGHOST/PGPORT visible to it.

For -o json or -o yaml, specify -c or -f; interactive psql uses text mode.

pg ps

Show PostgreSQL current connections. Queries pg_stat_activity view.

pig pg ps                         # Show client connections
pig pg ps -a                      # Show all connections (including system)
pig pg ps -u admin                # Filter by user
pig pg ps -d mydb                 # Filter by database

Options:

OptionShortDescription
--all-aShow all connections (including system)
--user-uFilter by user
--database-dFilter by database

pg kill

Terminate PostgreSQL connections. Default is dry-run mode, requires -x to execute.

pig pg kill                       # Show connections to be terminated (dry-run)
pig pg kill -x                    # Actually terminate connections
pig pg kill --pid 12345 -x        # Terminate specific PID
pig pg kill -u admin -x           # Terminate user's connections
pig pg kill -d mydb -x            # Terminate database connections
pig pg kill -s idle -x            # Terminate idle connections
pig pg kill --cancel -x           # Cancel queries instead of terminating
pig pg kill --watch 5 -x          # Repeat every 5 seconds
pig pg kill --plan                # Preview connection termination plan

Options:

OptionShortDescription
--execute-xActually execute (default is dry-run)
--pidTerminate specific PID
--user-uFilter by user
--database-dFilter by database
--state-sFilter by state (idle/active/idle in transaction)
--query-qFilter by query pattern
--all-aInclude non-client background processes
--cancel-cCancel queries instead of terminating
--watchRepeat every N seconds
--planPreview execution plan without terminating connections

--state accepts known connection states, including idle in transaction (quote values with spaces). --query matches query text without case sensitivity. A positive --pid selects that process and takes precedence over other filters. Without filters, the command selects other client sessions; --all also includes non-client backends.

pg clone

Create a database copy in the same instance. The command terminates sessions on the source database before copying, so schedule it when that interruption is acceptable. It uses CREATE DATABASE ... TEMPLATE; PostgreSQL 15+ adds STRATEGY FILE_COPY. PostgreSQL 14 is also supported with its default copy strategy.

pig pg clone meta                       # Clone meta as meta_1/meta_2/...
pig pg clone meta meta_fork            # Clone to a specific database name
pig pg clone meta meta_fork --owner dba # Try to change new database owner
pig pg clone meta meta_fork --port 5433 # Connect to a specific local port
pig pg clone meta meta_fork --plan      # Preview clone plan

Options:

OptionShortDescription
--portPostgreSQL port, default 5432 or $PG_PORT
--conn-dbConnection database: postgres, or template1 when cloning postgres
--ownerTry to change the owner of the cloned database
--conn-limitConnection limit for the new database (-1 unlimited, 0 disallow connections)
--planShow execution plan only
--yes-ySkip confirmation prompt

On PostgreSQL 18+ with file_copy_method=clone and a compatible filesystem, the copy can use copy-on-write (CoW). Otherwise it uses an ordinary copy. Use pg fork to copy an entire instance. Filesystem preflight runs as the selected database system user, including for a private 0700 data directory. Text mode requests confirmation; structured execution requires --yes.

Database Maintenance Commands

The [dbname] operand of vacuum, analyze, freeze, and repack accepts a database name. Values containing = or starting with postgres:// or postgresql:// are rejected as connection strings before planning, confirmation, or execution; errors do not echo the value. With --all, vacuum, analyze, and freeze validate the full database list before any maintenance runs. Use the native client when you need a connection string. Spaces and non-ASCII database names remain supported. For names beginning with -, put all options first and use -- before the name, for example pig pg vacuum --full --plan -- --all previews the single database named --all.

pg vacuum

Run SQL VACUUM through psql. The default database is postgres.

pig pg vacuum                     # Vacuum the postgres database
pig pg vacuum mydb                # Vacuum specific database
pig pg vacuum -a                  # Vacuum all databases
pig pg vacuum mydb -t mytable     # Vacuum specific table
pig pg vacuum mydb --schema myschema -t mytable  # Vacuum one table in a schema
pig pg vacuum mydb --full         # VACUUM FULL (requires exclusive lock)

Options:

OptionShortDescription
--all-aProcess all databases
--schemaSpecify schema
--table-tSpecify table
--verbose-VVerbose output
--full-FVACUUM FULL (requires exclusive lock)
--planShow the operation without executing it
--yes-ySkip VACUUM FULL confirmation

For vacuum and freeze, combine --schema with --table to select a table. To process a whole schema, use native vacuumdb --schema SCHEMA.

--full rewrites tables and needs an exclusive lock. Text mode asks for confirmation; structured execution requires --yes.

pg analyze

Run SQL ANALYZE through psql to update planner statistics. The default database is postgres.

pig pg analyze                    # Analyze the postgres database
pig pg ana                        # Alias
pig pg analyze mydb               # Analyze specific database
pig pg analyze -a                 # Analyze all databases
pig pg analyze mydb -t mytable    # Analyze specific table

Options:

OptionShortDescription

--table-tSpecify table
--verbose-VVerbose output

pg freeze

Run SQL VACUUM (FREEZE) through psql to freeze old transaction IDs. The default database is postgres.

pig pg freeze                     # Freeze the postgres database
pig pg freeze mydb                # Freeze specific database
pig pg freeze -a                  # Freeze all databases

Options: Same as pg analyze.

pg repack

Rebuild tables with pg_repack. Install the executable and the extension in each target database. The default database is postgres.

pig pg repack mydb                # Repack all tables in database
pig pg repack -a                  # Repack all databases
pig pg repack mydb -t mytable     # Repack specific table

pig pg repack mydb -j 4           # Use 4 parallel jobs
pig pg repack mydb --plan         # Preview target and command without running pg_repack

Options:

OptionShortDescription
--all-aProcess all databases
--schemaSpecify schema
--table-tSpecify table
--verbose-VVerbose output
--jobs-jNumber of parallel jobs (default 1)
--planShow tables to be repacked

Parameter Tuning Commands

pg tune

Generate starting values for memory, parallelism, and WAL settings. PIG uses the PostgreSQL version, CPU count, memory, disk capacity, and selected workload profile. The storage formulas assume SSDs. The command prints recommendations; it does not edit configuration files.

pig pg tune                       # auto-detect hardware, use oltp profile
pig pg tuning                     # alias
pig pg tune -p olap               # use OLAP profile
pig pg tune -p tiny               # for small instances
pig pg tune -c 8 -m 32768 -d 500  # override hardware detection
pig pg tune -C 500                # override max_connections
pig pg tune -R 0.30               # adjust shared_buffers ratio
pig pg tune -o json               # structured JSON output
pig pg tune -o yaml               # structured YAML output

Options:

OptionShortDefaultDescription
--profile-poltpTuning profile: oltp / olap / tiny / crit
--cpu-c0CPU cores, 0 means auto-detect
--mem-m0Total memory in MB, 0 means auto-detect
--disk-d0Data disk size in GB, 0 means auto-detect
--max-conn-C0Override max_connections, 0 uses profile default
--shmem-ratio-R0.25Fraction of memory used for shared_buffers, range 0.1 ~ 0.4

Profiles:

ProfileBest forCharacteristics
oltpGeneral transactional workloadsBalanced connection count, cache, and parallelism
olapAnalytical workloadsMore aggressive parallelism and work memory
tinySmall instancesConstrained memory footprint and parallelism
critLatency-sensitive workloadsRestricts parallel gather and favors stable response time

Notes:

  • Generated parameters are automatically gated by PostgreSQL major version. For example, io_workers is only emitted for PG 18+.
  • Text output includes a success message. Copy only the parameter assignments into your configuration; do not redirect the complete output into a PostgreSQL config file.
  • For scripts, use -o json and read data.parameters. Review the values, apply them through your configuration workflow, then reload or restart PostgreSQL as required.

Instance Fork

pg fork

Create a local one-off PostgreSQL physical copy for temporary analysis, troubleshooting, recovery validation, and development testing. Managed forks are written to /pg/data-<name> by default and are not registered with Pigsty, systemd, or Patroni. When --dst-data is specified explicitly, the command creates an unmanaged fork that is not enumerated by fork list.

pig pg fork dev                       # Create /pg/data-dev, do not start
pig pg fork init dev --start          # Create and start, probing ports from 15432
pig pg fork init dev -s --dst-port 15433    # Create and start on specified port
pig pg fork init dev -D /pg/data2 --src-port 15431  # Specify source dir and source port
pig pg fork init dev --dst-data /tmp/dev    # Create unmanaged fork
pig pg fork list                      # List managed forks
pig pg fork start dev                 # Start existing managed fork
pig pg fork stop dev                  # Stop existing managed fork
pig pg fork rm dev --stop             # Stop and remove a running fork
pig pg fork init dev --plan           # Show execution plan only

Create Options:

OptionShortDefaultDescription
--dst-data/pg/data-<name>Unmanaged target data directory
--dst-portauto-detectTarget port, probes free ports starting at 15432
--src-data/pg/data or $PG_DATASource data directory; can also be set globally with pg -D/--data
--src-port5432 or $PG_PORTSource port
--start-sfalseStart the fork after creation
--force-ffalseOverwrite an existing stopped target directory and skip confirmation
--timeout-t60Startup wait timeout in seconds
--yes-yfalseSkip confirmation prompt
--planfalseShow execution plan only

Management Commands:

CommandCommon OptionsDescription
pig pg fork list-o json/yamlList managed forks with optional structured output
pig pg fork start <name> or --dst-data <dir>--dst-data, --dst-port, -t/--timeout, --planStart existing fork
pig pg fork stop <name> or --dst-data <dir>--dst-data, -m/--mode, -t/--timeout, --planStop existing fork
pig pg fork rm <name> or --dst-data <dir>--dst-data, --stop, -m/--mode, -t/--timeout, -f/--force, -y/--yes, --planRemove fork; running forks require --stop

Behavior Notes:

  • When the source instance is running, the command uses PostgreSQL low-level backup APIs to create a consistent physical copy; when the source is stopped, it can perform a cold copy.
  • The command prefers CoW/reflink. If only ordinary copy is available, interactive mode warns about disk-space risk and waits for confirmation.
  • The target cannot be /, /pg, source PGDATA, or a parent/child of source PGDATA. Symlinks are resolved before checking the source/destination relationship. /pg/data follows the same ownership, relationship, and runtime checks as other data directories.
  • Replacing a nonempty unmanaged target requires valid unmanaged pg_fork metadata in fork.json with an explicitly recorded target.data matching the directory. An arbitrary directory without PG_VERSION is not eligible for deletion. Missing, damaged, incomplete, or mismatched metadata is refused. An empty directory remains usable with --force. Managed forks must be replaced by name. A running or uncertain destination cannot be replaced. Forced removal by name still permits cleanup of a managed orphan under /pg/data-<name>.
  • Path validation resolves private directories as DBSU when the caller cannot traverse them; unresolved paths and source/destination aliases are refused.
  • Unmanaged fork removal checks an inaccessible target as the selected DBSU. The target must be a real directory; a symlink or failed check still prevents removal.
  • After copy, runtime and replication state is cleaned from the fork and fork.json is written. The new instance starts only when -s|--start is specified.
  • Managed forks must be managed by name. Unmanaged forks require --dst-data when starting, stopping, or removing.

List Forks:

pig pg fork list scans /pg/data-*, reads fork.json, and refreshes each managed fork’s runtime state. Text output shows NAME, PORT, STATE, PID, AGE, SOURCE, COPY, and DATA; state is reported as running, stopped, orphan, or unknown. Unknown state sets runtime_unknown: true in structured output without claiming that the fork has started. Lifecycle operations fail without rewriting metadata in that state.

JSON and YAML put fork records in the result’s data array. Records include source and target endpoints, copy and backup metadata, management commands, and PIG build metadata.

Structured Output:

pig pg fork init dev --plan -o yaml
pig pg fork list -o json

pg log grep

Search log file content.

pig pg log grep ERROR             # Search for ERROR
pig pg log grep --ignore-case error  # Ignore case
pig pg log grep -C 3 ERROR        # Show context
pig pg log grep ERROR pg.csv      # Search specific log file

pg svc Subcommand

pg svc (also pg service or pg s) controls the postgres systemd unit used by Pigsty. It requires that unit to exist. For distribution units such as postgresql-18 or postgresql@18-main, use systemctl with the actual unit name.

pig pg svc start                 # Start postgres service
pig pg svc stop                  # Stop postgres service
pig pg svc restart               # Restart postgres service
pig pg svc reload                # Reload postgres service
pig pg svc status                # Show service status

Alias Reference:

CommandAlias
pg svc startboot, up
pg svc stophalt, dn, down
pg svc restartreboot, rt
pg svc reloadrl, hup
pg svc statusst, stat

Tools and privileges

PIG uses initdb to initialize data, pg_ctl to control instances, psql for SQL and maintenance, pg_repack to rebuild tables, and system tools to read logs. Use those tools directly for options that this command does not expose.

PostgreSQL commands run directly when you are the selected database operating-system user. From root, PIG uses su; from another account, it uses sudo -H -u. Service management uses root privileges. These commands target Linux; service management requires systemd.
